# BUG-14（P3）一张网查询偶发上游错误原样透传（前端看到 S3 XML）

> 级别：P3（偶发；但会直接暴露上游内部报文）
> 环境：AgenticKB v1.1.41
> 发现：2026-11-19；勘误：2026-11-28（见 §7——「OnenetQueryError 未接 → 500」的代码缺口属实；但根因链解释不了观测到的 400+S3 XML，`Bearer null` 归因、「400 不重试」、「token 空仍发请求」三处与代码相反，透传路径未定因）
> 状态：**代码缺口（异常未接 → 500）属实，未修复；400+S3 XML 的透传路径未定因**

## 1 现象

同一次 `POST /api/onenet/search`（条件 `source_site = ODN`，精确）：

- 第一次（09:5x）：HTTP 400，响应体是**对象存储的 S3 XML**：

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<Error><Code>InvalidArgument</Code>
<Message>Unsupported Authorization Type</Message>
<RequestId>…</RequestId><HostId>…</HostId>
<Authorization>Bearer null</Authorization></Error>
```

- 数分钟后同样请求：HTTP 200，正常 JSON `{"documents":[],"total_documents":0,...}`。

即：上游链路偶发失败，且失败时把内部报文（含 HostId/RequestId、鉴权头回显）原样透给前端。

（11-28 勘误：现象为运行期观测，仓库无法核实；且有两点与代码不符——①若走现行代码链，上游 400 会被退避重试满 3 次（1.5s/3s，约 4.5s+）后才以 **500** 返回，观测到的却是即时 **400 原文**；②前端 `handleError` 只显示 `${status}: ${axios message}`（`OnenetAdminView.vue:633-634`），**不渲染响应体**——「前端看到 S3 XML」只能发生在 DevTools 网络面板，界面弹出的会是 `500: Request failed with status code 500` 一类。见 §7 更正 1/5。）

## 2 影响

- 用户看到 XML 无法理解，也无从操作；
- 报文回显了鉴权头形态（`Bearer null`），对外部暴露了内部调用方式与凭据形态；
- 无法区分"上游故障 / 凭据失效 / 配置错误"。

（11-28 勘误：第二条不成立——`Bearer null` 不是本方任何一跳发出的字面值：`client.py:123` 发裸 token（无 Bearer 前缀）；前端只在 token 真值时才附加 `Bearer ${token}`（`proxyClient.ts:26-28`）；网关反代转发前剥掉 `authorization`（`proxy.py:33`）。该回显只能是上游/中间层的自身渲染，不构成对内部凭据形态的泄露。第三条对「未接住 → 500」路径成立（确实无法区分故障类别），对「透传 XML」路径未定因。见 §7 更正 3。）

## 3 根因分析

`knowledge_mining/mining/onenet/client.py`：

```python
def _post(self, body):
    r = self._http().post(self._search_url, json=body,
        headers={"Authorization": self.get_token(), ...})
    if r.status_code == 401 and attempt == 0:
        self.get_token(force=True); continue
    r.raise_for_status()          # ← 非 2xx 抛 httpx.HTTPStatusError
    j = r.json()
    ...
    raise OnenetQueryError("请求失败(%d次): %s" % (retry, last_err))
```

- `get_token()` 把 `Authorization` 头直接设为 token 串（无 `Bearer ` 前缀）；若上游实际要求 Bearer 形态，会出现 `Bearer null` 式回显（说明 token 为空或格式不符时仍发出了请求）。
- `raise_for_status()` 的错误被包成 `OnenetQueryError`，但 `routes.py` 的 `onenet_search`（约 118-139 行）**只 catch `ValueError`**：

```python
try:
    out = await asyncio.to_thread(search_documents, client, ...)
except ValueError as e:
    raise HTTPException(422, str(e)) from e
finally:
    client.close()
```

`OnenetQueryError` 逃逸 → 500。但本次观测到的是 400 + XML 原文，说明该 400 响应的**body 被上层原样返回**（可能来自代理层或 APIGW 直连路径），需服务端日志确认具体跳转。

（11-28 勘误：所引代码与「只 catch ValueError → OnenetQueryError 逃逸」属实，但该链的必然产物是 **500 generic**，解释不了观测到的 400+XML——①Starlette 对未捕获异常返回 500 `Internal Server Error`，不含异常文本，更不含上游 body；②实际安装的 httpx 0.28.1 的 `raise_for_status()` 消息只含状态码/URL/Mozilla 文档链接，**不含响应体**——`OnenetQueryError` 消息里根本没有 XML；③前端 onenet 请求实际走网关反代（`proxyClient.ts:56`，`/api/control-plane/api/v1/proxy/{domain}/mining`），网关用 StreamingResponse **原样回传 mining 响应**（`proxy.py:204-209`）——而 mining 不可能产出 400+XML，故透传不发生在这条链的任何一环。末句「需服务端日志确认」已自认未定因，本节标题实应读作"未定因分析"。另首条括注「token 为空……仍发出了请求」与代码相反：`get_token()` 在 result 为空时直接抛 `OnenetQueryError`（`client.py:110-111`），不会发出空 Authorization 的 search 请求。见 §7 更正 1/2/3。）

## 4 修复建议

1. `routes.py` 所有 onenet 端点统一 catch `OnenetQueryError`：

```python
except OnenetQueryError as e:
    logger.warning("onenet upstream failed: %s", e)
    raise HTTPException(502, {"code": "onenet_upstream_error",
                              "detail": "一张网查询服务暂时不可用，请稍后重试"}) from e
```

2. `client.py` 对非 2xx **不把响应体正文透出**，只保留状态码与稳定的错误类别：

```python
if r.status_code >= 400:
    raise OnenetQueryError(f"upstream_status={r.status_code}")
```

（原始报文只进服务端日志，且需截断、脱敏 `Authorization`。）

3. token 形态核对：确认上游要的是 `<token>` 还是 `Bearer <token>`；若 token 为空必须**在发请求前**抛错，绝不发 `Authorization: null`。

4. 重试策略：当前 `_retry` 内对 5xx/网络错误重试，`400` 不重试（正确）；但应把"鉴权类错误"单独归类（`onenet_auth_error`），便于运维判断是凭据问题而不是网络抖动。

（11-28 勘误后逐条核实——建议 1：缺口真实（search/probe/toc 均会 500），方向正确；但点名的 "imports" 端点上游调用在后台任务、HTTP 层不抛 `OnenetQueryError`，漏列了同步打上游的 **resync**（`routes.py:503-513` 只接 `ResyncError`）。建议 2：所防的「响应体透出」当前并不存在（httpx 0.28.1 消息无 body + 逃逸后是 generic 500）——真正会把上游文本带进异常消息的只有 `client.py:111`（token 端点 `res.text[:300]`）与 `client.py:136-137`（形状异常分支 `json.dumps(j)[:300]`），且都到不了前端；本条作为**建议 1 落地时的前置约束**仍有效（若把 `str(e)` 放进 502 detail，这两处文本就会外泄）。建议 3：后半句已是现状（`client.py:110-111`），非缺口。建议 4：前提错误——400 **会**被重试（`client.py:138` 的 `except (httpx.HTTPError, OnenetQueryError)` 涵盖 `HTTPStatusError`），「400 不重试」与代码相反，若照改属行为变更需明示。见 §7 更正 4、补充 1/2。）

## 5 验证

1. 人为把 `onenet.static_token` 置空 → 请求返回 502 `onenet_upstream_error`，**不含任何 XML/凭据信息**。
2. 恢复配置 → 查询返回 200。
3. 正常/空结果查询 → 仍 200（不误伤）。
4. 排查开关：服务端日志中可看到 `upstream_status=400` 与脱敏后的原始报文。

## 7 勘误记录（2026-11-28 核对）

核对方式：§3/§6 所引代码逐一静态核对（当前 master；自 v1.1.41 起相关文件仅 BUG-08 `fba3ae8` 动过 routes.py 的 4xx 文案常量，异常处理未变，文档描述与现状一致）；实际安装的 httpx 0.28.1 的 `raise_for_status()` 源码核验；前端 axios 链（`proxyClient.ts` / `OnenetAdminView.vue`）与网关反代（`main_control_service/proxy.py`）逐跳核对。未做动态复现——现象为偶发上游故障，本地无法构造。

属实部分：

- **代码引文与行号**：`_post` 结构（`client.py:117-143`：401-attempt0 强制重取、`raise_for_status`、重试耗尽抛 `OnenetQueryError`）；`get_token` 99-113；`onenet_search` 119-140（原文"约 118-139"，偏差 1 行内）；
- **`Authorization` 无 Bearer 前缀**：`client.py:123` 直填 `get_token()` 返回值；
- **`OnenetQueryError` 是 `RuntimeError` 子类**（`client.py:48`），`except ValueError` 接不住 → 逃逸；全仓无全局异常处理器 → FastAPI/Starlette 返回 500；
- **probe/toc 同缺口**：probe 只有 try/finally（`routes.py:151-154`）；toc 只接 ValueError→404（`routes.py:196-197`）；
- **上游为华为 APIGW**（`config.py:19-21`，apigw-cn-south02.huawei.com）——「APIGW」表述吻合；
- **上游失败被包成 `OnenetQueryError`** 属实（重试耗尽后 `client.py:143`）；
- **P3 定级合理**：现行代码链上用户最多看到无文案的 500；上游 XML 到不了前端（见更正 1），无数据泄露面。

原报更正（5 项）：

1. **根因链解释不了观测现象（核心硬伤）**：文档推断「`OnenetQueryError` 逃逸 → 500」，但观测是 **400 + XML 原文**。三个独立证据：Starlette 未捕获异常返回 generic 500（不含异常文本）；httpx 0.28.1 的 `raise_for_status()` 消息不含响应体（`OnenetQueryError` 消息里没有 XML）；网关 StreamingResponse 只原样回传 mining 响应（`proxy.py:204-209`）而 mining 产不出 400+XML。故 §3 实为**未定因**——透传发生在哪一跳未查明（原文末句已自认需服务端日志）；
2. **「token 为空或格式不符时仍发出了请求」**：相反。`get_token()` 在 result 为空时直接抛 `OnenetQueryError`（`client.py:110-111`），不会发出空 Authorization 的 search 请求；
3. **「`Bearer null` 回显暴露内部调用方式与凭据形态」（§2）**：归因不成立。三跳都发不出该字面值——client.py 裸 token 无 Bearer 前缀；前端仅 token 真值时附加 Bearer（`proxyClient.ts:26-28`）；网关转发前剥掉 authorization（`proxy.py:33`）。该串只能是上游/中间层对收到的鉴权头的自身渲染；
4. **「400 不重试（正确）」（§4.4）**：相反。`client.py:138` `except (httpx.HTTPError, OnenetQueryError)` 涵盖 `HTTPStatusError`，400 按退避重试满 3 次（sleep 1.5s/3s，`client.py:140-142`）。「若观测是即时 400 原文」这一点本身即佐证响应不是这条链产生的；
5. **「前端看到 S3 XML」的呈现位置**：`handleError` 只显示 `${status}: ${e.message}`（`OnenetAdminView.vue:633-634`，axios message，如 `Request failed with status code 400`），不渲染响应体——XML 只可能见于 DevTools 网络面板，UI 内不会出现。

补充（原报未发现）：

1. **会带上游文本进异常消息的只有两处，且都到不了前端**：`get_token` 的 `res.text[:300]`（token 端点响应体，`client.py:111`）与 `_post` 形状异常分支的 `json.dumps(j)[:300]`（`client.py:136-137`）。修复建议 1 落地时若把 `str(e)` 放进 502 detail，这两处文本就会外泄——建议 2 的截断/脱敏应作为建议 1 的前置而非独立项；
2. **resync 端点同样同步打上游且只接 `ResyncError`**（`routes.py:503-513`）——统一 catch 的端点清单应为 search/probe/toc/resync，不含 imports（后台任务）；
3. **前端 onenet 请求实际走网关反代**：baseURL 为 `/api/control-plane/api/v1/proxy/{domain}/mining`（`proxyClient.ts:56`）——排查 400+XML 来源时应核对网关反代与 mining 两级访问日志，而非只看 mining。

结论：定级 P3 维持。「`OnenetQueryError` 未接 → 500」的代码缺口属实、值得修（建议 1 方向正确，端点清单按补充 2 修正为 search/probe/toc/resync）；但观测现象（400+S3 XML 透传）与该缺口**无因果连接**，根因未定——需生产侧日志（网关反代/mining 访问日志）定位实际跳转后，再判断是否存在独立的透传缺陷。
