# BUG-15（P3，非缺陷）用户删除→恢复后无法直接启用，且接口路径与其它模块不一致（含11-28勘误）

> 级别：P3（账号运维体验）→ 11-28 勘误改判：**非缺陷**（恢复语义为 55号整改的刻意设计，UI 已有三层提示；残留两项体验改进见 §7 结论）
> 环境：AgenticKB v1.1.41
> 发现：2026-11-18（现象）、2026-11-19（复核）；勘误：2026-11-28（见 §7——核心机制属实，但"UI 没有任何提示""产品语义未明确"两条主论据与代码事实相反，复现命令有路径错误，根因描述不准确）
> 状态：**非缺陷（设计如此，已有提示）**（11-28 勘误前为：P3 账号运维体验问题，待修复）

## 1 现象

1. 用户 `restore` 后返回 200，但账号 `status=disabled`；若同时域授权被清空，`PATCH {"status":"active"}` 返回：

```
400 {"detail":"domain_grants_must_not_be_empty"}
```

即：恢复成功 ≠ 可用，用户需要先重新授域才能启用，但 UI 没有任何提示。

（11-28 勘误：前半句属实——restore 确实返回 `status=disabled`。但"若同时域授权被清空"的"若"字误导：delete 与 restore 都会级联清空域授权（`db.py:608-609`、`:639-640`），恢复后未重新授域时 `PATCH` **必然** 400，是确定性规则而非偶发。"UI 没有任何提示"**不属实**——UI 有三层提示且 v1.1.41 时已在场，见 §7 更正 1。）

2. 同一账号在 2026-11-19 复核时 `PATCH {"status":"active"}` 返回 200（说明该账号此时已有域授权）——因此现象与"授权是否被清空"相关，属**状态相关**而非稳定复现。

（11-28 勘误："状态相关而非稳定复现"是对确定性规则的误读。规则是："恢复后未重新授域 → 必然 400；重新授域 → 200"。11-19 复核得 200 只是因为中间重新授过域——原报自己也写了"说明该账号此时已有域授权"。）

3. 接口路径与其它模块不一致：用户管理挂在 `/api/kb/users...`（需注意 `/kb` 段），而知识库、检索等是 `/api/kb/{id}/...`、`/api/v1/...` 混用。本次测试第一次就因为漏 `/kb` 得到 404，排障成本高。

（11-28 勘误：归因错误。用户管理与知识库模块**同在** `/api/kb` 前缀下（`auth.py:46` 与 `kbs.py:26` 完全一致）；`/api/v1` 是控制面/LLM 任务中心（另一服务）的路径。本服务内路径风格统一为 `/api/<module>`（kb/ops/onenet/artifacts/workspaces/runs）。漏 `/kb` 得 404 的排障体验真实，但属跨服务路径并存问题，并非用户管理特例——且原报复现命令自己就写错了 DELETE 路径（§2、§7 更正 4）。）

## 2 复现

```bash
# 1) 软删 → 恢复
#（11-28 勘误：原报此步写作 DELETE "$BASE/api/kb/users/$UID"，会 404——实际路由是
#  /api/kb/admin/users/{uid}（auth.py:431），全服务不存在 DELETE /api/kb/users/{uid}。
#  以下为修正版。）
curl -X DELETE  "$BASE/api/kb/admin/users/$UID" -H "Authorization: Bearer $TOK" \
     -H 'Content-Type: application/json' -d '{"confirm_username":"<username>"}'
curl -X POST    "$BASE/api/kb/admin/users/$UID/restore" -H "Authorization: Bearer $TOK"
# → 200，status=disabled（且域授权、KB 成员、MCP 钥匙均已清空，site_role 降为 member、密码清空）

# 2) 直接启用
curl -X PATCH   "$BASE/api/kb/users/$UID" -H "Authorization: Bearer $TOK" \
     -H 'Content-Type: application/json' -d '{"status":"active"}'
# → 恢复后未重新授域：必然 400 domain_grants_must_not_be_empty
# → 重新授域后再 PATCH：200
```

## 3 根因（11-28 勘误：实为设计说明，非缺陷成因）

- `knowledge_mining/mining/kb/routes/auth.py`：
  - `restore`（约 453 行）只把 `deleted_at` 置空，不复原 `status` 与域授权；
  - `PATCH /users/{id}`（约 367 行）在 `status='active'` 时校验"必须至少有一个域授权"，但没有在 `restore` 阶段把这条约束前移。
- 产品语义未明确：软删时域授权是"级联删除"还是"保留待恢复"。

（11-28 勘误更正，两点：）

1. "只把 `deleted_at` 置空"严重低估了 restore 的实际动作。restore 共做六件事（`db.py:639-650`）：`deleted_at=NULL`、`status='disabled'`、`site_role` 降为 `member`、`password_hash=NULL`、删 `kb_members` + `user_domains`、吊销 mcp_keys；delete 同样级联清授权（`db.py:608-615`）。"恢复后需重新授域"正是这套清理的必然结果。
2. "产品语义未明确"不成立。语义在三个层面明确一致，且是 55号整改（`eb0b4fb`，2026-09-28，v1.1.12 起）的刻意设计：
   - DB docstring（`db.py:628`）：`"Restore the same identity as disabled and permission-empty."`（只恢复身份、权限清空）；
   - 单测（`test_user_lifecycle_policy.py:90-107`）：测试名 `test_delete_and_restore_preserve_identity_without_permissions`，断言 `restored["status"] == "disabled"`；集成测试 `test_user_lifecycle_integration.py:54` 同断言；
   - 前端恢复弹窗文案与之呼应（§7 更正 1）。

## 4 修复建议（11-28 勘误后：仅第 4 条前半仍成立，其余不成立）

1. **明确语义（推荐）**：软删只标记 `deleted_at + status=disabled`，**保留**域授权；恢复时把 `status` 恢复为 `active`（若授权仍在）。这样 restore 即恢复可用，符合"恢复"直觉。
   （11-28 勘误：语义**已经明确且与建议相反**——权限清空是刻意设计。此条等于推翻 55号整改的安全取向；如确要改，属需求变更，应另立需求单评估，不是缺陷修复。）
2. 若出于安全选择"恢复后需重新授权"，则：
   - `restore` 响应里返回 `{"status":"disabled","needs_grants":true}`；
   - UI 在恢复成功提示中明确"请先分配知识域再启用"；
   - 或提供 `restore?activate=true` 一次性完成（在授权仍存在时）。
   （11-28 勘误：现行实现即"恢复后需重新授权"方案，且前两条 UI 已做到（恢复弹窗 + 成功 toast，见 §7 更正 1）。剩余可做的只有响应体加机器可读字段（如 `needs_grants:true`）；`restore?activate=true` 在"授权必清空"的现行语义下无从生效，除非连语义一起改。）
3. `PATCH status=active` 的 400 文案改为可执行：

```
400 {"code":"domain_grants_must_not_be_empty",
     "detail":"启用前请先为该用户分配至少一个知识域（用户管理 → 域授权）"}
```

   （11-28 勘误：后端 detail 本就是稳定码 `domain_grants_must_not_be_empty`（`user_service.py:139`），前端已把它映射为中文"启用的普通用户至少需要一个知识域"（`managementError.ts:12` → `zh/common.ts:76`；启用入口 `UserManagementTab.vue:504-511` 走 `managementErrorMessage`）。裸 400 只在绕过 UI 直接 curl 时出现——对脚本调用方，稳定码本身即机器可读。）
4. 路径一致性：至少在帮助中心第 20 章列出"用户管理实际路径清单"；长期建议统一到 `/api/v1/users...`（保留旧路径做 1 个版本的 alias）。
   （11-28 勘误：前半**保留**——唯一成立的改进项；后半不成立——`/api/v1` 是控制面/LLM 任务中心（另一服务）的路径，本服务内风格已统一 `/api/<module>`，用户管理与 KB 模块同在 `/api/kb` 下，无需迁移。）

## 5 验证（11-28 勘误后：1-3 描述的是"方案 1"行为，与现行设计相反，仅在需求变更时适用；4 为既有行为、仍成立）

1. 软删一个带 1 个域授权的用户 → restore → `status=active` 且授权仍在（方案 1）。
2. 软删一个无授权的用户 → restore → 返回 `needs_grants:true`，UI 有明确引导；不出现裸 400。
3. 有授权的账号 `PATCH {"status":"active"}` → 200（回归，不应被新逻辑破坏）。
4. `DELETE` 时 `confirm_username` 不匹配 → 400（既有行为不变）。（核对成立：`user_service.py:170-171` + `auth.py:153-154`，单测 `test_user_lifecycle_policy.py:111-119` 在场。）

## 7 勘误记录（2026-11-28 核对）

核对方式：路由（`auth.py`）→ 业务（`user_service.py`）→ DB（`db.py`）三层逐条对照；前端提示文案用 `git log -S` / `git show v1.1.41:` 回溯确认在报告版本已在场；恢复语义另以单测/集成测试名与断言佐证。

属实部分：

- **restore 返回 200 且 `status=disabled`**：`db.py:647-656`（v1.1.41 同版语义）；
- **空授权时 `PATCH {"status":"active"}` → 400 `domain_grants_must_not_be_empty`**：`user_service.py:136-139`（member 启用须 ≥1 授权）+ `auth.py:153-154`（UserError→400）；
- **恢复后必须先重新授域才能启用**：属实，且是确定性的（见更正 3）；
- **行号准确**：restore 453 / PATCH 367 / 域授权 489-585；
- **§6 所列文件均存在**。

原报更正（5 项）：

1. **"UI 没有任何提示"——错**。三层提示，且经 `git show v1.1.41:` 核对**全部在报告版本已在场**（55号整改 `eb0b4fb`，2026-09-28，v1.1.12 起）：
   - 恢复确认弹窗（`UserManagementTab.vue:627`）："恢复 {username}？账号将保持禁用，且不会恢复历史域权限、KB 成员关系或 MCP 钥匙。"
   - 恢复成功 toast（`:633`）："用户已恢复为禁用账号，请重新分配域后再启用"
   - 启用失败错误码映射（v1.1.41 时为 `managementError.ts` 内联文案，现为 `managementError.ts:12` → `zh/common.ts:76`）："启用的普通用户至少需要一个知识域"

   原报的观测全部来自 curl，未走 UI。
2. **"产品语义未明确"——错**。`db.py:628` docstring `"Restore the same identity as disabled and permission-empty."` + 单测测试名 `test_delete_and_restore_preserve_identity_without_permissions` + 前端弹窗文案，三处一致声明"仅恢复身份、权限清空"——这是刻意设计，不是未定义行为。
3. **"状态相关而非稳定复现"系误读**。delete 与 restore 都级联清空授权（`db.py:608-609`、`:639-640`），故"恢复后未重新授域 → PATCH 必然 400"是确定性规则；11-19 复核得 200 只因中间重新授过域。另根因"restore 只把 deleted_at 置空"不准确——实际六件事见 §3 勘误注。
4. **复现命令第 1 步路径错误**：DELETE 实为 `/api/kb/admin/users/{uid}`（`auth.py:431`），原报的 `/api/kb/users/{uid}` 会 404。原报抱怨路径易混淆，自己的复现命令恰好踩了同一个坑——这本身反而是"帮助中心缺路径清单"最有力的论据。
5. **"接口路径与其它模块不一致"归因错误**：用户管理与知识库模块同在 `/api/kb` 前缀（`auth.py:46` = `kbs.py:26`）；`/api/v1` 属控制面/LLM 任务中心（另一服务）；本服务内风格统一 `/api/<module>`（kb/ops/onenet/artifacts/workspaces/runs）。

结论：**改判非缺陷（设计如此，已有提示）**。原报 P3 的两条主论据（UI 无提示、语义未明）均被推翻；站得住的只剩"裸 curl 恢复后不能直接启用"这一现象本身，而它是已声明的设计。残留两项体验改进（不构成缺陷，择机排期即可）：

- 帮助中心第 20 章补"用户管理实际路径清单"——重点标注 DELETE 与 restore 都在 `/api/kb/admin/users/{id}` 下（本次原报即踩此坑）；
- （可选）`restore` 响应体加机器可读字段（如 `needs_grants:true`），方便脚本调用方；当前只有 UI 文案引导。

若产品确要改为"恢复即保留授权并 active"，属需求变更而非缺陷修复，应另立需求单评估安全影响（与 55号整改取向相反）。
