# BUG-12（P3，待确认）检索记录疑似重复打点：同一次 MCP 调用出现两条记录

> 级别：P3（统计可信度；若确认会导致 MCP 调用量翻倍）
> 环境：AgenticKB v1.1.41
> 发现：2026-11-19；勘误：2026-11-28（见 §7——代码描述属实；但 §4 验证 SQL 一处硬伤、§3 两个根因假设与代码事实矛盾，且原始数据已在所有可达环境丢失、现象不可复现）
> 状态：**现象观测属实（当时 UI 层面），原始数据已丢失、根因不可验证，待重新观测**（11-28 勘误前为"现象确凿，根因待服务端验证"）

## 1 现象

`/retrieval-records` 明细中，多条 MCP 调用成对出现，且**同一时间戳 + 同一耗时**：

```
2026-11-17 17:24:29  admin  MCP  get_knowledge  wiki_links · structure    成功  48 ms
2026-11-17 17:24:29  admin  MCP  get_knowledge  wiki_links · structure    成功  48 ms
2026-11-17 17:22:20  admin  MCP  get_knowledge  wiki_search · structure   成功  53 ms
2026-11-17 17:22:20  admin  MCP  get_knowledge  wiki_search · structure   成功  53 ms
2026-11-17 17:20:58 / 17:20:47 / 17:22:04 同样成对
```

同一秒、同一毫秒级耗时，基本排除"用户真的点了两次"（人手重复点击不可能出现完全相同的耗时）。

（11-28 勘误：成对两行连 tool/action 列都完全相同，意味着两行都出自 MCP middleware——Java 侧记录的 tool_name 恒为 NULL，渲染不出 `get_knowledge · wiki_links · structure`，见 §7 更正 2。另注：成对两行在 DB 中必然 id 不同——id 为主键，同 id 不可能两行，见 §7 更正 3。）

## 2 影响（若确认）

- `summary.sources.mcp` 与 `tools[*].calls` 翻倍；
- 零结果率/失败率分母被放大，分析结论失真；
- 明细页噪音，用户难以定位真实调用。

## 3 现有设计（说明这不是"完全没考虑"）

- `mcp_server` 在工具调用开始时写一条 `pending` 记录，结束时**用同一 id** 更新（`mcp_server/server.py:274`、`:296`，`_safe_post_access_record(..., phase="create"/"complete")`）。
- `knowledge_mining/mining/infra/retrieval_records_db.py` 的 upsert 带抑制逻辑：仅当来源为 mcp、状态非 pending、且 `details_json->>'terminal_owner'='serving'` 时才更新（约 111-120 行）。
- 已有回归测试 `mcp_server/tests/test_access_records.py::test_search_tool_writes_one_safe_record_and_suppresses_java_duplicate`（同文件约 124 行），说明"Java(serving) 侧也会写一条，需要被抑制"。

因此重复的可能来源：
1. serving（Java）侧写入的重复记录与 mcp 侧 id 不同，抑制条件未命中；（11-28 勘误：与现象矛盾，就本现象可排除——Java 侧记录 tool_name 恒为 NULL、operation 硬编码 'search'、details 无 action/ref_type，UI 不可能渲染成成对行的样子；且 X-KB-Access-Id 在场时 Java 以同一 id 写入、由 upsert 合并。见 §7 更正 2）
2. 同一 id 的 create/complete 在特定时序下被插成两行（例如 create 重试）；（11-28 勘误：物理不可能——`id TEXT PRIMARY KEY`，同 id 两行无法存在，见 §7 更正 3）
3. 网关代理重试（客户端超时后重发）导致两次真实调用。（11-28 勘误：排除前两条后仅存的主要假设；但两次真实执行出现完全相同的毫秒级耗时概率极低，此点至今存疑，见 §7 补充）

## 4 验证方法（服务端执行）

```sql
-- 1) 是否存在"同秒同耗时"的成对记录
SELECT occurred_at, actor_username, tool_name, duration_ms, COUNT(*) AS n
FROM knowledge_access_records
WHERE source='mcp' AND occurred_at >= now() - interval '7 days'
GROUP BY 1,2,3,4 HAVING COUNT(*) > 1 ORDER BY 1 DESC LIMIT 50;

-- 2) 成对记录的 id / details_json 差异（重点看 terminal_owner、payload 是否存在）
SELECT id, occurred_at, status, duration_ms, details_json
FROM knowledge_access_records
WHERE occurred_at = '<上面某一秒>' ORDER BY id;

-- 3) 是否同一 mcp_key 的同一请求（payload request_json 是否完全相同）
--（11-28 勘误：原报此条 SQL 会直接报错——payloads 表主键是 record_id、没有 id 列，
--  且 request_sha256 列不存在（全库仅 response_sha256），见 §7 更正 1。以下为修正版）
SELECT r.id, p.request_json->>'query' AS q, p.request_json->>'ref' AS ref,
       p.response_sha256, p.request_bytes
FROM knowledge_access_records r LEFT JOIN knowledge_access_record_payloads p ON p.record_id = r.id
WHERE r.occurred_at = '<某一秒>';
```

判定标准（11-28 勘误后）：两条记录 `id` 不同（必然——同 id 不可能两行）且 `request_json` 完全相同、`duration_ms` 相同 → 强烈提示同一请求被写/执行两次；`response_sha256` 也相同则响应内容亦一致。原报判定标准引用了不存在的 `request_sha256` 列，见 §7 更正 1。

## 5 修复方向（按验证结果选）

- 若为 serving 重复：把抑制条件改为"同 domain + 同 actor + 同 tool + 同 request_sha256 且在 ±N 秒内"去重，或让 serving 侧不再写 mcp 来源记录（单一写入口）。（11-28 勘误：就本现象 serving 重复已可排除（§7 更正 2），此条降级为一般性防御；其中 request_sha256 同样是库里不存在的列、需现算）
- 若为 create 重试：`post_access_record` 的 create 阶段加幂等键（请求级 `call_id`），服务端按 `call_id` upsert。（11-28 勘误：该幂等键已存在——create 即携带请求级 call_id，id 为主键、upsert 天然幂等，同 call_id 的任何重试都不会产生第二行；真正可能产生第二行的是"重发"（新 tools/call → 新 call_id），需要请求内容指纹 + 时间窗的去重，见 §7 更正 4）
- 若为客户端重试：mcp_server 对 tools/call 加"同 session + 同参数 + 5s 内"合并。（11-28 勘误后：这是仅存的针对性修复方向——对应唯一存活的假设 3）

## 7 勘误记录（2026-11-28 核对）

核对方式：§3/§6 所引四处代码逐一核对；对成对现象做了三环境实查——生产 39.96.13.112（应用容器经 172.30.30.1 网桥实连 pg 容器的 `coremasterkb_v2` 库）、远程测试 PG 121.89.90.178、本地 PG 18（端口 15432）。

属实部分：

- **双阶段写与同一 id**：`mcp_server/server.py:253`（`call_id = str(uuid.uuid4())`）→ `:274` create（pending）/`:296` complete，两阶段共用同一 id；
- **upsert 抑制条件**：`knowledge_mining/mining/infra/retrieval_records_db.py:110-121`；完整条件比原报概述多两项（增量也须 `terminal_owner='mcp'` 且非 pending），简化描述方向正确；
- **回归测试存在**：`mcp_server/tests/test_access_records.py:124` `test_search_tool_writes_one_safe_record_and_suppresses_java_duplicate`；
- **"Java(serving) 侧也会写一条"属实**：`agent_serving_java/.../observability/QueryLogAspect.java:24`（切 `ParadigmExecutionService.run`）→ `KnowledgeAccessRecordService.java:136`（source=mcp 时 details 置 `terminal_owner:'serving'`）；
- **时间线吻合**：v1.1.41 确为 2026-11-17 发布（releases.json）；`wiki_search`/`wiki_links` 视图真实存在（`InternalArtifactController.java:240/259`）；且 11-17 之后写入路径仅 BUG-11 一处改动（未动 middleware/upsert）——本次核对的代码即当时的代码。

原报更正（4 项）：

1. **§4 SQL 3 与判定标准引用不存在的列**：`knowledge_access_record_payloads` 主键为 `record_id`（没有 `id` 列），且全库不存在 `request_sha256` 列（仅 `response_sha256`，见 016 DDL）——`request_sha256` 在整个代码库中仅出现在本文档自身。原 SQL 会直接报 column does not exist，§4 已替换为修正版；
2. **§3 假设 1（serving 侧不同 id 重复）与现象矛盾，可排除**：Java 侧写入的记录 tool_name 恒为 NULL（`KnowledgeAccessRecordService.build()` 从不设置该字段）、operation 硬编码 `'search'`、details 只有 engine/output 等键——这样一行在 UI 不可能渲染成 `get_knowledge · wiki_links · structure`；且 X-KB-Access-Id 在场时 Java 以同一 id 写入（`build()` 中 `nonBlank(args.accessId(), UUID.randomUUID())`），由 upsert 合并。成对两行连 tool/action 都相同，只能都出自 MCP middleware；
3. **§3 假设 2（同 id 插成两行）物理不可能**：`id TEXT PRIMARY KEY`（`databases/kb/schemas/015_knowledge_access_records.sql:5`）。任何重复必然是不同 id，即两次独立的 `on_call_tool` 执行；
4. **§5"create 加幂等键"针对的缺陷已不存在**：create 阶段本就携带请求级 call_id 且 id 为主键、upsert 幂等。可能产生第二行的是"重发"（每次重发是新的 tools/call、新 call_id），需要请求内容指纹级去重，而非 call_id 幂等。

补充（原报未发现）：

- **原始数据已全部丢失、现象不可复现**：生产 `coremasterkb_v2` 全表 19 行（2026-10-26 → 11-19），**11-16~11-18 之间 0 行，且从未有过任何 get_knowledge 记录**（仅 web search ×5 与本体三工具 ×14）；远程测试 PG `kb_db` 无此表（`kb_db_test` 有但 0 行）；本地 PG 18 五个库均无此表。原报"现象确凿"只能成立于当时 UI 层面的观测，现在既无法确认也无法证伪；
- **现有生产数据无此现象**：同秒成组的行 duration 均不同、id 不同（真实并行/连续调用），不存在"同秒同耗时"对；
- **写入方清单（一次 MCP get_knowledge 调用）**：① mcp_server middleware——唯一会写 tool_name=get_knowledge + action/ref_type 的写入方；② Java QueryLogAspect——仅 paradigm run 路径，同 id 合并；③ mining mcp_tools——仅 manage_files 上传完成，同 id。列表页为单表 `SELECT *` 整页替换 + 游标分页（`RetrievalRecordsPanel.vue:291` `records.value = page.items`），前端与服务端都不存在重复行机制；
- **唯一存活的解释是假设 3**（宿主/网关真实重发两次 tools/call），但"多次成对且毫秒级耗时完全相同"对两次独立执行而言概率极低，此点至今无解。若再次观测到成对记录，第一步应对比两行的 `id` 与 payload 的 `request_json`/`response_sha256`（§4 修正版 SQL）：id 不同且 request_json 相同即坐实"同一请求执行两次"，再看 duration/response 是否也相同以区分"重放同一结果"与"真实二次执行"。
