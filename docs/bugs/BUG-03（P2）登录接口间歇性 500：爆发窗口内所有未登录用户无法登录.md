# BUG-03（P2）登录接口间歇性 500：爆发窗口内所有未登录用户无法登录

> 级别：P2（可用性；影响所有新会话）
> 环境：AgenticKB v1.1.41
> 发现：2026-11-18（首次）、2026-11-19（复现）
> 复核：2026-11-26 对照 master 3863742 与 v1.1.41（80aa4f0）逐项核实并修正——PUT /system/{service}/raw 并不级联 reload-auth-config（该扇出仅存在于显式 POST /api/v1/admin/reload-auth）；API 写 YAML 自首个提交（0dd66ca，2026-07-24）起即 tempfile+os.replace 原子写；auth 配置为内存缓存、无重载窗口；identify 失败分支为 502 非 401。根因嫌疑据此从 API 写路径改指**部署通道的非原子拷贝**（deploy-sync scp 直拷）
> 修复：2026-11-26 落地（§7）。落地时再次勘误：deploy-sync pack/apply 两侧均不触碰 `main_control_service/config/`（铁律，见 §3 修正版），"标准发布流直拷配置"通道不存在；非原子写者只能是服务器上的**带外操作**（手工 scp/编辑）。修复据此按"读侧对任意写者免疫"设计，不依赖确认具体写者。

## 1 现象

- `POST /api/control-plane/api/v1/auth/identify` 与 `.../auth/login` 返回 **500 纯文本 `Internal Server Error`**（Starlette 默认未捕获异常输出，无 JSON 结构、无 detail）。
- 爆发期间其它**带有效 token** 的接口全部正常（知识库列表、检索、系统配置均 200），说明不是网关/服务整体宕机。
- 持续时间：2026-11-19 一次观测窗口约 3 分钟（10:07~10:10），期间连续 3 次 identify 均 500；2026-11-18 亦出现过两轮。
- 恢复后立即连续 20 次 identify 请求 **20/20 成功**，说明不是永久性配置损坏，而是瞬时/间歇故障。
- 影响面：任何未持有 JWT 的用户（新登录、token 过期 12h 后、被踢下线后）在此窗口内完全无法进入平台。

## 2 复现

```bash
# 爆发窗口内：5xx 纯文本
curl -s -w '%{http_code}' -X POST "$BASE/api/control-plane/api/v1/auth/identify" \
     -H 'Content-Type: application/json' --data '{"username":"admin"}'
# → 500 "Internal Server Error"

# 同期带 token 的接口正常
curl -s -w '%{http_code}' -H "Authorization: Bearer $TOKEN" \
     "$BASE/api/control-plane/api/v1/system"
# → 200
```

> 注意：本机直连时不要走系统 HTTP 代理（`curl --noproxy '*'`），否则会得到代理层 504 页面，与本缺陷混淆。

## 3 根因分析（待服务端日志确认）

`main_control_service/main.py` 的 `login`（152 行）与 `identify`（193 行）handler 结构（两 handler 无兜底 try/except，未捕获异常即裸 500）：

```python
body = await request.json()
...
for entry in service.list_domains():          # ① 读域配置——未被 try/except 包
    svcs = service.get_domain_services(did)   # ② 已被 try/except 包住（异常 → continue）
    ...
result = await verify_user_via_mining(...)    # ③ 内部异常已被吞，返回 None → login 401 / identify 502
```

按代码阅读（v1.1.41 与当前 master 一致）：`verify_user_via_mining`（main.py:41-58）吞掉所有异常返回 `None`，login 返 401、identify 返 502，都**不是** 500。500 只可能来自：

1. `request.json()` 解析失败（排查用同 body 的其他请求，可能性低）；
2. **`service.list_domains()` 抛异常（最强候选）**：它不在 try/except 内，且**每请求读盘**——先读 `domain_registry.yaml`，再逐域读 `scenario_packs/{pack}/domain.yaml`（service.py:90-102、228-231，无任何缓存）。任一文件瞬时不可解析（`yaml.safe_load` 抛 YAMLError；根非映射时 `payload.get` 抛 AttributeError）→ 未捕获 → 500。与观测自洽的点：**带 token 的代理接口只读 registry**（`reverse_proxy` → `get_domain_services`），不碰 scenario pack——若瞬时坏的是某个 pack 文件，恰好只有 login/identify 这对入口 500，其余全 200。
   （注意 `get_domain_services` 的异常已被 ② 包住，不可能 500；能炸的只有 `list_domains` 这一行。）

已排除的候选（复核结论）：

- ~~`_find_auth_mw` / `jwt_encode` / `jwt_secret` 瞬时读不到~~：auth 配置是**内存缓存**（`AuthMiddleware._state`，启动时 `reload()` 装载；`reload()` 用单次赋值原子换引用，无中间态窗口），每请求不读盘。secret 缺失/占位符时中间件在 SKIP_PATHS **之前**就返回 503（auth.py:243-244），到不了 handler；`jwt_encode` 对正常输入不抛异常。
- ~~进程内配置缓存被 `reload-auth-config` 清空后的重载窗口~~：**该级联不存在**。`PUT /api/v1/system/{service}/raw` 只对 `llm_service` 做热加载通知（main.py:250-263），与 auth 无关；`reload-auth-config` 扇出只存在于显式管理端点 `POST /api/v1/admin/reload-auth`（main.py:608-649，c032e8c 2026-08-07 引入），前端与部署脚本均无自动调用（全库 grep 证实）。即便触发，mining 侧重拉失败也只会让 verify 拒绝 → 401/502，不是 500。

**关键线索（二次修正版）**：控制面 API 的 YAML 写入自首个提交起就是原子的（`_save_yaml`/`_save_yaml_text`：tempfile.mkstemp + `os.replace`）——**API 路径不存在"读到半截文件"**。上一版怀疑的"deploy-sync scp 直拷配置"通道经实码核实**不存在**：deploy-sync 两条铁律明确永不触碰 `main_control_service/config/`——pack 侧 `rm -rf "$PACK_STAGE/main_control_service/config"`（打包前剔除），apply 侧 `find "$dir" -mindepth 1 -maxdepth 1 ! -name config -exec rm -rf {} +`（同步时保留）；deploy-server.sh 对 config 只做存在性校验、从不写入（全库 grep：Python 侧仅 `YamlConfigService` 写这些文件，tools/reset_*.py 只读）。发布流中的 "scp" 指传输 sync-*.tar.gz 归档到服务器，不是拷配置文件。

剩余候选写者：**服务器上的带外操作**——运维手工 scp/rsync 单个配置文件或直接编辑（`echo >` / 编辑器 truncate-write），约 3 分钟窗口与一次手工同步/编辑吻合。此假设需服务器侧日志确认（见下），但**修复不依赖确认**：读侧快照回退对任意写者的瞬时坏态免疫。

需在服务器侧确认（修复后仍值得核对，用于归因）：
- `main_control_service` 日志中爆发时段是否出现 `auth.login failed` / `auth.identify failed` / `yaml 读取失败，降级用上一份快照`（修复前为裸 Traceback 打到 stderr，修复后为结构化 503 + WARNING/ERROR 日志）。
- 爆发窗口（11-18、11-19 10:07-10:10）与服务器上 config 目录 mtime 变更（`ls -l --time-style=full-iso` / audit 日志）的时间相关性。

## 4 修复建议（2026-11-26 已全部落地，见 §7）

1. **止血（低风险，先做）——✅ 已实施**：给两个 handler 包一层兜底，把未知异常转成可诊断响应，而不是裸 500：

```python
try:
    ...  # 现有逻辑
except Exception as exc:  # noqa: BLE001
    logger.exception("auth.login failed username=%s", username)
    return JSONResponse(status_code=503, content={
        "detail": "auth backend temporarily unavailable", "code": "auth_upstream_unavailable",
    })
```

2. **读侧容错/缓存——✅ 已实施**：`list_domains()` 已确认每请求读盘（registry + 逐域 pack，无缓存）。改为 **(mtime_ns, size) 键控的快照缓存**（`_load_yaml_cached`）：键未变直接命中缓存（顺带消掉热路径重复解析）；解析失败/根非映射时**降级用上一份好快照并 WARNING 告警**；从未成功读过才抛出（此时由第 1 条兜底成可诊断 503）。合法写盘（API 原子写或手工编辑）mtime 变化 → 缓存即时失效，不吃陈旧配置。另加形状守卫：registry 根/`domains` 段/域条目/services 段非映射时降级（空注册表/跳过该域），不再 AttributeError。
3. **写侧收口（二次修正：无缺口可收）**：`update_system_config_yaml` 与域/包文件写入**不需要改**（自 init 起即 tempfile+os.replace）；deploy-sync/deploy-server **本就不触碰 config/**（§3 二次修正）。若运维确有手工 scp 配置文件的习惯，操作规范上应改为"scp 到临时文件 + mv 原子替换"——但这属于操作纪律，修复（第 2 条读侧免疫）不依赖它。
4. **可观测——✅ 已实施**：auth 入口进程内最小指标（login/identify 各计 total / errors_5xx / total_seconds→avg_ms），`GET /api/v1/admin/auth-stats` 读取（admin-only，重启归零）；兜底触发时 `logger.exception` 落完整 Traceback，可经 `/api/v1/logs` 在 UI 查看。

## 5 验证（自动化回归已覆盖 3/4，压测 1/2 待生产发布后执行，见 §7）

1. 修复后压测：并发 50 个 identify 请求 × 100 轮，0 个 5xx。
2. 在 `PUT /api/v1/system/auth/raw` 保存的同时，另一线程持续 identify 200 次，应 0 个 5xx（验证 API 原子写在读侧无窗口——本就应通过，作为回归基线）。
3. **模拟带外通道——✅ 自动化**：用 truncate-write 方式（模拟手工 scp 直拷）重写 `domain_registry.yaml` / `scenario_packs/*/domain.yaml` 的同时持续 identify/login——修复前会出 500（复现根因），修复后读上一份快照正常返回，且进程不崩溃。
4. **坏配置冷启动——✅ 自动化**：人为把 `domain_registry.yaml` 改成非法 YAML（含根非映射变体）：登录/identify 返回 503（`code=auth_upstream_unavailable`，可诊断）而不是裸 500；曾读到过好配置则降级快照正常返回。
   （注意：改 `auth.yaml` 测不到本路径——运行中进程用它的是内存缓存，盘上文件变更不触发任何行为；要测必须走 `POST /api/v1/admin/reload-auth` 或直接改 registry/pack。）

## 7 修复记录（2026-11-26）

**改动**（对照 §4 四条建议）：

1. `main.py`：`login`/`identify` 重写——非法 JSON/非对象 body → 400（`_json_object`）；业务未知异常 → 兜底 503 `{"detail": "auth backend temporarily unavailable", "code": "auth_upstream_unavailable"}` + `logger.exception`；两 handler 重复的"任一启用域 mining_url 发现"块提取为 `_first_enabled_mining_url`。
2. `service.py`：`_load_yaml_cached`（(mtime_ns, size) 键控快照缓存；解析失败/根非映射 → WARNING + 上一份好快照；从未成功过 → 抛出交兜底）；`_load_domain_registry`/`_load_scenario_pack` 改走缓存；形状守卫（`domains` 非映射→空注册表、域条目非映射→跳过/404、`services` 非映射→502）落到 `list_domains`/`get_domain`/`get_domain_services`/`get_serving_config`/`mining_internal_base_url`。
3. 可观测：进程内计数 `auth_stats`（login/identify 各 total/errors_5xx/total_seconds），`GET /api/v1/admin/auth-stats` 输出（含 avg_ms），admin-only（`/api/v1/admin/*` 既有分层）。
4. 测试：`main_control_service/tests/test_auth_resilience.py` 12 例全绿；`main_control_service/tests` 全量 111 通过 + 4 例既有环境红（`TestClient.__init__() got an unexpected keyword argument 'client'`，本地 httpx/starlette 版本不兼容，stash 复跑定性与本修复无关）。

**行为变化**：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| registry/pack 瞬时坏态（曾读过好配置） | 裸 500 纯文本 | 降级上一份快照，请求正常 200 |
| registry/pack 冷启动即坏 | 裸 500 纯文本 | 503 JSON `code=auth_upstream_unavailable`，日志含完整 Traceback |
| registry 解析成功但 `domains`/条目/`services` 非映射 | AttributeError 裸 500 | 降级（空注册表→503 可诊断 / 跳过该域 / 502） |
| body 非法 JSON / JSON 数组 | 裸 500 纯文本 | 400 JSON |
| 每请求 registry+pack 解析开销 | 每次全量读盘解析 | mtime 未变命中缓存 |
