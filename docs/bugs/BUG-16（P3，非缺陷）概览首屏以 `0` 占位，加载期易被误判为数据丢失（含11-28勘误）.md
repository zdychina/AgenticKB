# BUG-16（P3，非缺陷）概览首屏以 `0` 占位，加载期易被误判为数据丢失（含11-28勘误）

> 级别：P3（观感/误导）→ 11-28 勘误改判：**非缺陷**（所述根因 `ref(0)` 在代码里不存在，四条修复建议在报告版本 v1.1.41 已全部在场；残留一项体验改进见 §7 结论）
> 环境：AgenticKB v1.1.41
> 发现：2026-11-18；勘误：2026-11-28（见 §7——文件/接口定位准确，但"根因"与"未区分加载态"两条主论据与代码事实相反；"0 → 跳变"现象真实存在，但位置不是知识库卡片，而是区块标题栏的口径徽标）
> 状态：**非缺陷（所述问题在报告版本即已修复）**（11-28 勘误前为：P3 观感/误导，待修复）

## 1 现象

首次进入 `/`（概览）时，知识库卡片先渲染 `0 个知识库`，接口返回后跳变为真实值（如 7）。慢查询或弱网下该状态可持续数秒。

测试过程中一度据此判断"知识库被清空"，刷新后才确认是加载态。

（11-28 勘误：**"0 → 跳变"的现象存在，但位置不是"知识库卡片"**。卡片本体——区块 1 数字条与区块 4"我的知识库"——加载期显示的是骨架屏（shimmer 占位块），不显示 0（`DashboardView.vue:32-34`、`:185-187`，v1.1.41 已在场）。真正闪 0 的是**区块标题栏的口径徽标**：区块 1 头部"口径：本域我可见的 {n} 个知识库"（master 修前 `:25`）与挖掘趋势头部"共 {docs} 篇 · {runs} 次挖掘"（master 修前 `:121`）——这两枚徽标在 loading 门控之外，首载 `stats=null`、`kbs=[]` 时按兜底逻辑渲染出 0，接口返回后跳变。慢网下"本域我可见的 0 个知识库"确实可持续数秒——原报的观察大概率来自这里，但"知识库卡片先渲染 0"的定位错误。）

## 2 复现

1. 打开 DevTools → Network 限速（Slow 3G）。
2. 访问 `/` → 观察卡片 `0` 持续显示数秒后跳变。

（11-28 勘误：步骤本身可用。修前在限速下能观察到的是**区块 1 标题栏右侧的小徽标**"口径：本域我可见的 0 个知识库"持续数秒后跳变；下方四张统计卡与"我的知识库"卡片区均为骨架屏。原报没有区分这两层，把徽标的行为记到了卡片头上。）

## 3 根因（11-28 勘误：根因描述与代码不符）

`kb-ui/src/views/DashboardView.vue`（概览页）用 `ref(0)` / `ref([])` 初始化统计与列表，模板直接渲染数值，未区分"未加载"与"确实为 0"。相关统计接口为 `/api/kb/overview`、`/api/kb/stats`（`knowledge_mining/mining/kb/routes/overview.py`）。

（11-28 勘误更正，三点：）

1. **"`ref(0)` 初始化统计"——代码里不存在，且从未存在过**。统计是 `const stats = ref<KbStats | null>(null)`（master 修前 `:285`，v1.1.41 为 `:283`）——`null` 即未加载，恰是原报 §4 建议 1 自己提议的写法。以 `git show` 回溯三个时点核对：当前 master、报告版本 `v1.1.41`、乃至最初引入统计仪表盘的 `2acdcb8`（"概览页改为统计仪表盘"）——第一版就是 `null` + loading 三态，`ref(0)` 在这份文件的全部历史上没有出现过。
2. **"模板直接渲染数值，未区分'未加载'与'确实为 0'"——不成立**。数字条是三态门控：`statsLoading && !stats` → 骨架屏；`statsError && !stats` → BlockError（加载失败 + 重试）；否则才渲染数字（master 修前 `:32-36`）。列表区同理（`:185-188`）。"我的知识库"空态是专门的 EmptyState"还没有知识库"（`:197`）——正是 §4 建议 4 要的"后端明确返回 0 才出现的空态文案"。
3. 列表用 `ref([])` 初始化属实（`kbs` / `recentRuns`），但被 loading 门控，不产生所述现象——这半句对，结论错。

   真实的残留根因（范围比原报小得多）：两枚**区块标题栏口径徽标**位于各区块的 loading 门控之外——徽标取值 `stats?.kb_count ?? kbs.length` 与 `trendTotals(stats)`，首载时分别兜底到 0 与 0/0，数据到达后跳变。

## 4 修复建议（11-28 勘误后：四条在报告版本 v1.1.41 已全部在场）

1. 用 `null` 表示未加载，模板渲染 `—` 或骨架屏：

```ts
const stats = ref<Stats | null>(null)
// 模板：{{ stats ? stats.kb_count : '—' }}
```

   （11-28 勘误：**已是现状**——`ref<KbStats | null>(null)` 就在那里；模板走的是骨架屏分支而非 `'—'`，效果等价且信息量更大。）
2. 或统一骨架屏组件（`el-skeleton`），在 `loading=true` 时占位。
   （11-28 勘误：**已是现状**——自研 shimmer 骨架（`.dash__skeleton` 系列，1.4s 循环动画），非 `el-skeleton` 但功能等价，`2acdcb8` 引入当天就在。）
3. 空态与错误态分开：接口失败显示"统计加载失败，重试"按钮，而不是 0。
   （11-28 勘误：**已是现状**——BlockError 函数式组件（master 修前 `:264-272`），文案"加载失败"+ 重试按钮；三个数据源各记各的 error，单块失败不牵连其余；另有 staleRefreshError 横幅"刷新失败，显示上次数据"。）
4. 卡片文案区分："0 个知识库（暂无）"仅在后端明确返回 0 时出现。
   （11-28 勘误：**已是现状**——EmptyState"还没有知识库"+ 新建按钮，仅 overview 加载完成且列表为空时出现；区块 3 图表同原则（无任何库时整块换成空态引导，注释明言"一排 0 会被读成系统没在干活"）。）

## 7 勘误记录（2026-11-28 核对）

核对方式：当前 master 全文读 `DashboardView.vue` 与 `overview.py`；`git show v1.1.41:kb-ui/src/views/DashboardView.vue` 回到报告版本逐段比对；再回溯 `2acdcb8`（统计仪表盘引入提交）确认加载态设计的引入时点；前端调用路径对照 `src/api/kb.ts`。

属实部分：

- **§6 文件与行号定位准确**：`overview.py:77` 正是 `@router.get("/overview")`，`:125` 正是 `@router.get("/stats")`；前端确实调 `/api/kb/overview`、`/api/kb/stats`；
- **"0 → 跳变"现象真实存在**，但仅在两枚口径徽标上（见 §1 勘误注）；v1.1.41 与当前 master 行为一致，不存在"报告后修好了"的时间差；
- 列表 `ref([])` 初始化属实（但被门控，无所述后果）。

原报更正（3 项）：

1. **"`ref(0)` 初始化统计"——从未存在**。三个时点（master / v1.1.41 / `2acdcb8` 引入版）都是 `ref<KbStats | null>(null)` + loading 三态。根因描述指向一份不存在的代码。
2. **"未区分'未加载'与'确实为 0'"——与代码相反**。骨架屏 / BlockError / EmptyState / 旧值保留（同域刷新不闪、切域即清）四套机制齐备，恰好覆盖 §4 全部四条建议——建议清单等于现状清单。
3. **现象定位错位**：闪 0 的不是"知识库卡片"（卡片加载期为骨架屏），是区块标题栏的口径徽标。原报大概看到了真实的 0 → 跳变，但把它归到了错误的元素和不存在的实现上。

结论：**改判非缺陷（所述根因不存在，建议已全部在场）**。残留一项体验改进：两枚口径徽标加载期 0 占位 → 跳变（真实、可复现、P3 观感级；**已于同日实施，见 §8**）。
