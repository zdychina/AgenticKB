# BUG-02（P2）上传接口无文件类型白名单：任意扩展名都能入库

> 级别：P2（数据污染 + 与产品文案不一致 + 可被当作任意文件暂存）
> 环境：AgenticKB v1.1.41
> 发现：2026-11-19，上传 `virus.exe` 复现
> 复核：2026-11-26 对照 master 0a47c29（upstream v1.2.2 合并后）逐项核实，行号按当前代码修正；偏差点已改写——状态口径、魔数校验实际挂载路径（仅替换路径，上传路径连内容校验都没有）、白名单集合漏 chm/hdx、悬空的 BUG-07 引用
> 修复：2026-11-26 落地——`intake_upload` 前置白名单 + 归档成员整包预检；成员口径 = 文档格式 ∪ 资产格式（批次2b"含图片资产"决策保留）；回归 88 用例全绿（§6 表内行号为修复前快照）

## 1 现象

- 通过 `POST /api/kb/{kb_id}/documents`（multipart）上传 `virus.exe`（内容任意）→ **HTTP 201**，文档入库成功，响应 `status="uploaded"`；随后自动挖掘入队，列表派生态转 `mining`。
- 自动挖掘在解析阶段失败，文档状态变 `failed`，Run 变成 `completed + failed_count=1`。
- UI 上传区文案明确写："支持 Markdown、文本、HTML、PDF、Word（.doc/.docx）、Excel（.xls/.xlsx）及 ZIP 等格式"（`kb-ui/src/locales/zh/kbManage.ts:150`，en 版 151 行同义）。
- 即：**前端承诺白名单，后端不校验**，用户可在库里堆任意二进制文件，且只能在几分钟后的挖掘失败里才发现。
- MCP 入口同样失守：`PUT /api/kb/mcp-tools/upload-direct/{ticket}` 与网页上传同源走 `intake_upload`（`routes/mcp_tools.py:598`），Agent 侧上传 `.exe` 一样入库。

## 2 复现

```bash
curl -X POST "$BASE/api/kb/$KB/documents" \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@virus.exe"
# → 201 {"document_name":"virus.exe","status":"uploaded","auto_mined":true,...}
```

同一天同一库内：`.md` 上传 201（正常），`.exe` 也是 201（异常）。

## 3 根因

写入路径 `knowledge_mining/mining/kb/services/document_service.py`：

- 入库只按扩展名推断 MIME（`_EXTENSION_MIME`，48-68 行），**未知扩展名回落 `application/octet-stream`**（78 行），不拒绝。
- 魔数校验 `_validate_magic_bytes()`（178-213 行）**根本不在上传路径上**：它挂在 `_store_source_stream` 的 `expect_suffix` 守卫后（486-487 行），全库唯一传该参数的调用点是**替换路径** `replace_content`（949 行；`_store_source_stream` docstring 自述"只挂替换路径"）。即初次上传与归档成员入库**连内容校验都没有**——伪装成 `.pdf`/`.docx` 的随机字节同样 201。该函数对未知扩展名的放行逻辑：

```python
_MAGIC_SIGNATURES = {
    ".pdf": (b"%PDF-",), ".zip": (b"PK\x03\x04", b"PK\x05\x06"),
    ".docx": (...), ".xlsx": (...), ".pptx": (...),
}
expected = _MAGIC_SIGNATURES.get(suffix)
if not expected:
    return          # ← 未知扩展名直接放行（且此函数目前仅替换路径调用）
```

- 源码注释（166-167 行）明确写着"md/txt/html/json/chm/hdx 等无廉价可靠签名，**维持挖掘层失败兜底**"——即当前是"事后兜底"设计，没有前置白名单。
- 配置层同样没有口子：`UploadConfig`（`infra/upload_config.py`）只有 root/大小上限/归档扩展名（`.zip .hdx .chm`），无 allowed_exts 类配置。

## 4 修复

在 `intake_upload`（`document_service.py:316`，网页与 MCP 的同源收敛入口）增加扩展名白名单，与后端支持表对齐：

```python
# 直接从 MIME 回落表派生，两者永不脱节（.chm/.hdx 是正式支持的归档格式，
# 见 UploadConfig.archive_exts_set 与 _EXTENSION_MIME）
_ALLOWED_EXTS = frozenset(_EXTENSION_MIME)
# = {".md", ".markdown", ".txt", ".html", ".htm", ".pdf", ".doc", ".docx",
#     ".xls", ".xlsx", ".ppt", ".pptx", ".csv", ".json", ".zip", ".chm", ".hdx"}

def _validate_extension(filename: str) -> None:
    ext = Path(filename).suffix.lower()
    if ext not in _ALLOWED_EXTS:
        raise ValueError(
            f"不支持的文件类型 {ext or '(无扩展名)'}；"
            f"支持：{'、'.join(sorted(e[1:] for e in _ALLOWED_EXTS))}"
        )
```

抛 `ValueError` 即可：三条路由都已把 `ValueError` 映射为 400（网页上传 `routes/documents.py:194-195`；网页替换 `:355-356`；MCP `routes/mcp_tools.py:631-634`）。**不建议只挂在网页路由层**——会漏掉 MCP `upload-direct` 入口。

注意：
- 归档成员（zip 内文件）同样需要过一遍白名单，否则可用合法 zip 夹带 `.exe` 入库；`upload_archive_path` 成员分支（765-770 行，走 `upload_stream`）也要收敛。
- **成员口径（2026-11-26 定）**：成员白名单 = `_ALLOWED_EXTS ∪ _ARCHIVE_ASSET_EXTS`（图片 png/jpg/jpeg/gif/svg/bmp/webp/ico + CHM 部件 hhc/hhk/hhp + css）——批次2b"全部入库，含图片等资产"决策（2026-08-27）保留，真实 hdx/chm 包不被误伤；可执行/任意二进制仍整包拒绝。
- 白名单不要手写清单：从 `_EXTENSION_MIME` 派生可避免漏掉 `.chm`/`.hdx` 这类正式支持的归档格式（手写初版就漏过）。
- 若产品希望兼容"暂时未知格式"，应改为显式配置项 `upload.allowed_exts`（默认上面集合），而不是硬编码。

## 5 验证

1. `POST` `.exe` → 400，文案含支持列表，库内文档数不变。
2. `.md` / `.pdf` / `.docx` / `.zip` / `.chm` / `.hdx` → 仍 201（后两者走归档解压链）。
3. zip 内含 `.exe` 的归档 → **已实现为整包 400**：解压后、建目录/入库前预检，错误列出全部越界成员（前 10 个 + 总数），无部分入库残留。
4. 替换路径回归：伪装成 `.docx` 的随机字节走替换接口（`POST /api/kb/{kb_id}/documents/{document_id}/content`）仍 400——`_validate_magic_bytes` 只挂替换路径，本修复不应改变该行为。
5. MCP 回归：`upload-direct` 传 `.exe` 同样 400（与网页共用 `intake_upload`）。
6. 已知边界（不在本 BUG 修复范围）：扩展名合法但内容伪造的文件（如随机字节存成 `.pdf`）在上传路径仍会 201——上传路径本就没有魔数校验，白名单只按扩展名挡；如需上传侧内容校验，须把 `expect_suffix` 接进 `upload_stream`，建议另行立项。
