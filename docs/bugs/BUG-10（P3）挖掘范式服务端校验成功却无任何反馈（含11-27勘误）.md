# BUG-10（P3）挖掘范式"服务端校验"成功却无任何反馈

> 级别：P3（交互误导：用户会以为校验没跑）
> 环境：AgenticKB v1.1.41 发现；2026-11-27 在 master（1.1.54）逐条核对
> 发现：2026-11-19；勘误：2026-11-27（见 §7——核心事实属实（P3 维持），两处更正/补充）

## 1 现象

在 `/mining/workflows/{id}` 编辑器点击"服务端校验"：

- 网络面板可见 `POST /api/mining-workflows/{id}/validate` 返回 200 且 `{"valid":true,"errors":[],"executionPlan":{...}}`；
- 但页面右下角"校验结果"面板**仍显示**：

```
校验结果  通过
本地规则通过；发布前仍需服务端校验。
```

即：服务端校验已通过，文案却还在提示"仍需服务端校验"，用户无法判断校验是否真的执行过。

## 2 复现

1. 打开任一挖掘范式编辑器（如 `system-hybrid-assets`）。
2. 点"服务端校验"，观察面板文案不变。
3. 抓包确认 `valid:true`。

## 3 根因

`kb-ui/src/components/mining/workflow/WorkflowValidationPanel.vue:27-35`：

```ts
const allIssues = computed(() => [
  ...props.localIssues,
  ...(props.serverResult?.errors ?? []).map(...),
])
```

模板第 7 行：

```html
<p v-if="!allIssues.length" class="validation-panel__empty">本地规则通过；发布前仍需服务端校验。</p>
```

- 面板只根据"有没有 issues"决定文案，**完全不读 `serverResult.valid`**；
- `WorkflowEditorView.vue:579-591` 的 `validateOnServer()` 只是把结果塞进 `serverResult`，没有 toast，也没有"已校验"时间戳。

（11-27 核对：两点均属实——`WorkflowValidationPanel.vue:27-35` 的 `allIssues` 与模板第 7 行文案逐字一致，组件内无任何地方读 `serverResult.valid`；`validateOnServer()` 成功路径只写 `serverResult`，无 toast、无时间戳。两处补充：请求**异常**路径有 error toast，无反馈仅指成功路径；校验按钮本身已有 `:loading="validating"`（`WorkflowEditorView.vue:16`），但属瞬态，成功后界面回到原样，"用户以为校验没跑"的判断成立。）

## 4 修复建议

区分三态并在面板显示：

```ts
type ValidationState = 'idle' | 'server-pass' | 'server-fail' | 'running'
```

- `idle`（未校验）：保持现文案；
- `server-pass`：显示"服务端校验通过（HH:mm:ss）"，绿色 ✓，并展示 `executionPlan` 的执行顺序（已有数据，可直接渲染一行 `input_ingest → document_parse → …`）；
- `server-fail`：红色，逐条 error（现有列表）；
- 校验按钮 `loading` 时面板显示"校验中…"；
- （11-27 补充）同步补齐 `undo()`/`redo()` 的结果失效：二者（`WorkflowEditorView.vue:331-343`）直接 `applyGraph()`，不走 `recordMutation`、不清 `serverResult`——校验后撤销/重做改图，面板会残留旧校验结果（见 §7 更正 2）。与普通编辑的 idle 失效同一语义：改图即失效。

另外补一句 toast（`ElMessage.success('服务端校验通过')`），与"发布新版本"的成功提示风格一致。

新增一个派生属性：

```ts
const serverPassed = computed(() => !!props.serverResult?.valid && !(props.serverResult?.errors?.length))
```

模板改为：

```html
<p v-if="!allIssues.length && !serverPassed" ...>本地规则通过；发布前仍需服务端校验。</p>
<p v-else-if="serverPassed" class="validation-panel__ok">服务端校验通过 · {{ serverCheckedAt }}</p>
```

## 5 验证

1. 点"服务端校验" → 面板出现"服务端校验通过 + 时间"，toast 提示一次。
2. 手工造一个非法图（如断开必填连线）→ 服务端返回 `valid:false` → 面板红色列出 errors，发布按钮前提示"校验未通过"。
3. 修改图（dirty）后 → 面板回到 idle 态（结果失效），避免用旧结果误导发布。（11-27 勘误：普通编辑路径现状已具备——`recordMutation()` 在图真变化时清空 `serverResult`（`WorkflowEditorView.vue:317`），本条是"保持现状"而非新工作；undo/redo 路径不具备，见第 5 条。）
4. 发布流程（`publishWorkflow`，`WorkflowEditorView.vue:593-615`）仍按 `validation.valid` 判定，不被 UI 改动影响。
5. （11-27 新增）校验（通过或失败）后执行 undo 或 redo → 面板同步回 idle 态，不残留旧校验结果（现状会残留——undo/redo 未清 `serverResult`）。

## 7 勘误记录（2026-11-27 核对）

核心事实逐条核对**全部属实**，定级 P3 维持：

- 面板只看 issues 数、不读 `valid`：`WorkflowValidationPanel.vue:27-35` 的 `allIssues` 与模板第 7 行文案逐字属实，组件内无任何地方读 `serverResult.valid`；`valid:true, errors:[]` 时 `allIssues` 不变 → 文案停留在"仍需服务端校验"，Bug 确凿；
- `validateOnServer()` 行号（579-591）与行为属实：成功路径只写 `serverResult`，无 toast、无时间戳；
- API 端点属实：`miningWorkflow.ts:51-53` 确为 `POST /api/mining-workflows/{id}/validate`；
- 响应结构属实：`types/miningWorkflow.ts:145-157` 定义 `valid`/`errors`/`executionPlan`；
- `publishWorkflow()` 行号（593-615）与判定属实：`WorkflowEditorView.vue:599` `if (!validation?.valid)`。

原报两处更正/补充：

1. **§5 验证 3 并非待新增工作**：普通编辑走 `recordMutation()`，图真变化时已清空 `serverResult`（`WorkflowEditorView.vue:317`）→ 面板已回 idle 态。该条对普通编辑是现状已有的保护，修复时保持即可，不需要新实现（仅 undo/redo 缺失，见下条）；
2. **伴生问题（原报未发现）**：`undo()`/`redo()`（`WorkflowEditorView.vue:331-343`）直接 `applyGraph()`，不走 `recordMutation`、不清 `serverResult` → 校验后撤销/重做改图，面板仍显示旧校验结果。已纳入 §4 修复建议与 §5 验证 5，修复时应一并处理。

小处措辞（不影响结论）：面板位于右侧 inspector 侧栏（`.workflow-editor__inspector`，`border-left` 布局，`WorkflowEditorView.vue:727`）中的一个 section，§1"页面右下角"为大致描述。

## 8 修复记录（2026-11-27）

方案：面板内派生分支而非显式枚举状态机——`validating` / issues 列表 / `serverPassed` / idle 四分支互斥，标题徽标同步区分"校验中…（琥珀）/ N 项问题（红）/ 服务端通过（绿）/ 本地通过（绿，idle 从原"通过"精确化）"。§4 建议的 `serverPassed` 派生属性、通过态文案（含 HH:mm:ss 时间戳）、`executionPlan` 执行顺序单行渲染、成功 toast 均落地；执行顺序按编译器/运行时语义 input → document → global 三段拼接（节点 id，`compiler.py:224-238`）。

§7 勘误两项的落地：

- **undo/redo 失效**：新增统一 `invalidateServerResult()`（清 `serverResult` + `serverCheckedAt`），recordMutation / undo / redo / 版本预览 / 退出预览 / 恢复版本 / 重载共**七处**改图路径全部调用——"改图即失效"对一切图切换路径成立（previewVersion/exitPreview/restoreVersion/load 为同一原则的自然延伸，超出 §5.3 的最小范围）；
- **toast 打点**：`validateOnServer({ notify })` 增加开关，发布流程内部校验传 `notify:false`，避免"服务端校验通过"与"已发布不可变新版本"两个 toast 连发。
