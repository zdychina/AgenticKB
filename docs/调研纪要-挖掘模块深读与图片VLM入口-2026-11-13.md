## 第一部分：knowledge_mining 模块总体理解

### 1. 定位

CMKB 六服务中的**挖掘服务**：原始文档（md/txt/html/pdf/doc(x)/xls(x)/zip/chm/hdx/一张网）→ 结构化知识资产，供 agent_serving 检索。FastAPI 应用工厂 `mining/api/app.py:294 create_app`，18 个 router ≈ 180 端点。

### 2. 两代链路

| | legacy 链 | workflow 链（正式） |
|---|---|---|
| 入口 | `jobs/run.py:_run_legacy` + `pipeline.py` StreamingPipeline | `mining/workflow/` 算子化 DAG runtime |
| 现状 | 仅剩兼容分支；`_publish_legacy`/`_resume_legacy` 已退役 | 新建 Run 一律 `execution_engine="workflow"` |
| 默认绑定 | — | 无显式指定时自动绑 `system-hybrid-assets.current_version`（冻结 manifest） |

### 3. 正式链全景（上传 → 发布）

```
上传 POST /api/kb/{kb_id}/documents
  → DocumentService.intake_upload（分块 sha256 → MinIO 内容寻址 source bucket）
  → auto_mine 入队（AsyncDomainRunRepository 落 queued + 冻结 manifest）
  → DomainRunQueueDispatcher（每域单线程 FIFO，interrupted 优先 + 租约 fencing）
  → jobs/run._execute_workflow_job（300s 租约 × 30s 心跳）
  → MiningWorkflowRuntime.execute()  三 zone：
     ├─ input 串行：input_ingest（KB 增量判定 NEW/SKIP/RETRY/UPDATE）
     ├─ document 并行（有界线程池 + persist marker 断点恢复）：
     │    document_parse          冻结输入→ParsePlan→解析尝试链→质量门→不可变快照
     │    segment_compile         Parse IR → 切片（v2.1 纯函数，直写 asset_raw_segments）
     │    retrieval_unit_project  确定性投影 11 类检索表示（无 LLM）
     │    embedding / query_expansion / hierarchical_summary（可选，FALLBACK）
     │    asset_persist           三面资产写 7 张 v2 staging 表（只 stage 不 commit）
     └─ global 串行：mining_finalize
          readiness 门禁 → staging→final 晋升（唯一入口 promote_snapshot_assets,
          infra/db.py:848）→ Build 组装校验 → 发布 release
```

### 4. 子系统要点速览

- **Workflow 引擎**：算子契约 `MiningOperatorDef`（core.py:325）；编译器做槽类型/zone 单向性/能力传播校验（compiler.py）；manifest 带 paramsHash+graphHash 防篡改；文档级并行中多前驱分支按 run_document_id 合流（`merge_batches`）；错误策略五档 FAIL_FAST / SKIP_DOCUMENT / SKIP_WITH_EMPTY / FALLBACK / PAUSE_FOR_REVIEW。
- **解析链**：Parse IR 是扁平 elements + parent_of 关系（非嵌套树），9 种容器 / 22 种元素类型 / EvidenceSpan 四类定位；native adapters（docx/xlsx/pptx/html/pdf/onenet）；质量门五值 PASS/WARN/REPAIR/FALLBACK/FAIL 驱动 backend 回退；reconciler 跨页结构修复；幂等锚点是 snapshot_fingerprint（不是 parse run 行）。
- **切片编译 v2.1**：纯函数零 IO；标题链、家具过滤、表格 whole/rows/both、表格/图片为原子单元、小片合并、semantic_role+table_kind 标注；指纹变化→复用同一 IR 重切不重解析。
- **检索投影 + 持久化**：11 类 representation；三面资产（raw 直写 + 结构面 + 表示面/向量 staging）；readiness 五能力（search/dense/structure_navigate/structured_query/aggregate），degraded 阻止晋升与发 Build；staging→final 只在 finalize 发布事务内晋升一次。
- **LLM 集成**：llm_service(:8900)；`LlmTaskClient`（直连，不吞错，批量轮询单一 deadline）；idempotency_key = 完整请求载荷 sha256；生成类失败一律降级不阻断基础资产。
- **服务层**：多域架构以 `domain_registry.yaml` 为唯一真相源；全局 control 库（workflow 定义 + KB 元数据）/ 域库（run + 资产）/ MinIO 三分；认证 = 网关注入 X-KB-User + 内部密钥；wiki 编译 = 增量质心聚类 + 六步管线。

## 第二部分：图片 VLM 识别入口专项调研

### 背景（需求原话）

> 在挖掘的时候，之前是否有一个入口留有 png 识别，需要配置多模态大模型。需要配置默认提示词+多模态大模型在切片的时候直接抽取 png 内部信息，形成对应的检索单元。

### 1. 入口确实存在 —— `ImageCaptioner`

位置 `mining/stages/image_caption/__init__.py:27`，与需求描述的形态完全一致：

- **挂载点在切片阶段内部**：`pipeline.py:421 _caption_tree_for_segment` 在 segment_stage 里、segmenter 运行之前遍历解析树，对 `block_type="image"` 且图注为空的块调 VLM 生成图注写回块 `text` → 图注文本随后进入切片 raw_text → 形成检索单元。
- **默认提示词已内置**（`image_caption/__init__.py:20-24`）：
  > 请用一两句中文描述这张图在技术文档中的含义。关注图中的结构、标注、流程或关键对象；不要编造看不清的细节。只输出图注正文，不要前缀「图注：」。

  system 提示「你是技术文档图注助手。」；文档已有原生图注会拼进 prompt 作参考（:124-127）。
- **默认多模态模型 `glm-4.5v`**（:19），经 llm_service 多模态通道（`llm_service.providers.multimodal.build_vision_user_message`），默认走异步任务通道 `submit_chat(model=...)` → 轮询；异步参数从 `MiningConfig` 取（`jobs/run.py:1841 _init_image_captioner`）。
- **开关**：环境变量 `MINING_ENABLE_IMAGE_CAPTION`（默认**关**，run.py:1827）；workflow 参数 `enableImageCaption / imageCaptionModel / maxImagesPerDoc`（`options.py:30-32`）。
- **兜底纪律**：失败回落原生图注或 `[image p.N]` 占位；每文档上限默认 20 张；永不阻断文档。

### 2. 但该入口在现行 v2 正式链上已断线

| 事实 | 依据 |
|---|---|
| `ParseSegmentOptions` 官方注释："legacy 保留，故意不注册进 v2 目录" | `workflow/operators/options.py:16-20` |
| 唯一调用它的 handler 是 v1 遗留算子 `parse_segment_handler`，不在现行 9 算子目录 | `workflow/handlers/document.py:77-88` |
| 现行默认模板走 `document_parse → segment_compile`，segment_compile 是纯确定性编译、零 LLM | `segment_compiler/compiler.py` |
| v2 链里 figure 只有自带 caption/文本才成片，无图注无文本直接丢弃（「不伪造」纪律） | `compiler.py:631 _emit_figure` |

即：`MINING_ENABLE_IMAGE_CAPTION=1` 只对已退役的 legacy 链生效；现行挖掘 run（workflow 引擎 + hybrid 模板）里图片 VLM 识别**不会执行**。

### 3. v2 链对图片的现状矩阵

| 来源 | 解析抽取 | 说明 |
|---|---|---|
| PPTX 内嵌图片 | ✅ 已抽取 | picture → figure 元素 + sha256 二进制资产 |
| DOCX 内嵌图片 | ❌ 仅计数诊断 | 不抽取字节、不产 figure 元素 |
| PDF 内嵌图片 | ❌ 完全不抽 | `native_pdf.py` 无 figure 逻辑（pdfplumber 只做文本/表格） |
| 独立 PNG/JPG/GIF 文件 | ❌ unsupported | 上传白名单**允许**（`safe_intake.py:77-79`），但解析路由只剩未配置的 `cloud_vlm` 占位槽（`parse_adapters/registry.py:44-49`）→ `unsupported_format`（`file_inspector/router.py:78`） |

投影侧配套是现成的：projector 矩阵已有 `figure → figure_caption` 表示类型——只要切片里有带文本的 figure 片段，检索单元自动形成。

### 4. 结论与方案方向

要在现行 v2 链实现「切片时抽取 PNG 内部信息 → 形成检索单元」，需补开发。两个方案（详细设计见关联文档）：

- **方案 A（解析面内嵌）**：VLM 图注作为 document_parse 的增强子步骤，图注写入 Parse IR 的 `FigureAsset.derived_annotations`（契约预留字段，`parse_ir/types.py:205`），随快照沉淀；segment_compile 与投影无感知联动。数据在快照层沉淀，重切/重投影都能用。
- **方案 B（算子面外挂）**：新增第 10 个可选算子 `image_caption_generate`（FALLBACK 语义），插在 segment_compile 与 retrieval_unit_project 之间，读快照 IR 的 figure/二进制资产生成图注并补插 figure 切片；不动解析器与编译器，改动面最小。

两方案共享同一前置（PDF/DOCX 图片字节抽取、独立 PNG 直通解析）与同一图注缓存设计。
