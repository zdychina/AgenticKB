## 一、一句话结论

newsfc-graph 不是一个待集成的功能，**它是 46/48/49/50 号规划了但尚未写一行代码的「知识制品」那一层的一套已验证实现**（实跑 2 万+ 对象）。本次移植的实质是：把它从绑死华为 5G 核心网的形态，抽象成 CoreMasterKB 的 `KnowledgeAsset` 载体与运行时，并接上 50 号的 DSH 制作闭环。

不移植它的平台外壳（独立 SQLite、独立用户/KEY、独立 MCP 服务、独立前端、文档导出器）——那六处在 CoreMasterKB 已有更强的实现。

## 二、已确定的决策

| # | 决策 | 说明 |
|---|---|---|
| D1 | 制品能力是 `knowledge_mining` 里的新模块 | 不新起第 7 个服务。它与 kb/域/鉴权/快照强耦合，独立服务会把 50 号的票据校验做成跨服务调用 |
| D2 | 制品正文走 MinIO，索引走 PG | 复用 `008_object_storage_foundation` 的 `asset_storage_objects` / `asset_storage_object_refs`；**不引 SQLite** |
| D3 | 制品载体 = md 文档 + frontmatter + `[[ID]]` 边 | newsfc 形态。制品之间成图、可逐层下钻。newsfc 的 md 解析/边/逻辑ID 代码全部可用 |
| D4 | 一个制品 = 一批 md 对象 | 不是「一篇 md 一个制品」。submit 分批提交，草稿按对象维护 |
| D5 | 类型与骨架两级 | 平台 registry 定「该类制品必须有哪些 frontmatter 字段 + 逻辑ID 几段 + 哪些必备章节」；单个制品再在骨架上补自己的业务字段和对象规则 |
| D6 | 制品不允许跨知识域 | 一个制品只能选同一 domain 下的文档，制品表落该域的 `asset_core` 库，与现有域路由一致 |
| D7 | 远端 Agent = DSH（deepseek-harness） | 按 50 号实现平台侧原生会话适配器，DSH 侧不改代码 |
| D8 | 审核不通过 = 同一制作实例续跑 | 审核意见作为新一轮消息发进同一会话，Agent 重新 `get_creation_context` 后提交新修订 |
| D9 | 首期范围 = 只做制作闭环 | 不做消费面 MCP 工具族、不做前端制品浏览页、不做完整入图闸门 |

**D9 的一处加项**：D4（一批对象）与 D9（不做闸门）叠加会让人审失去抓手。首期做**最小 diff**——新增/修改/删除三类清单 + 单对象前后对比；**不做**沙箱构建、覆盖/只新增/撤销三选、按任务回退。

## 四、制品规范体系：抽走元规范，丢掉业务层包

newsfc 的四个层包（命令/特性/Task/业务）内容是华为 5G 专有的，但它们**同构的那个结构**是领域无关的，正是 48 号缺的 `MethodPackage` 骨架：

```text
{制品类型}/
  agent.md          构建师人设（角色/职责边界/输入输出/交接）
  SKILL.md          构建方法（体裁：Spec 代码构建 / Procedure Agent 手工）
  字段定义.md       该类制品对象的字段权威表
  template/         md 文件骨架
  check.md          核查清单（只审不建）
  change-requests/  变更请求闭环
```

与 D5「两级」的对应关系：

| 层包文件 | 落到哪 | 为什么 |
|---|---|---|
| `字段定义.md` / `template/` / `check.md` | **平台库内，做版本化的制品定义** | 50 号要求「制品定义修订」保存在平台；Agent 要通过 `get_creation_context` 读到它们 |
| `agent.md` / `SKILL.md` | **仓库文档** | 是给人和构建 Agent 读的方法论，不是每制品一份 |
| `change-requests/` | 二期，接 46 号「候选与审核工作台」 | 首期用审核驳回意见代替 |

同时抽走顶层的 `演进机制.md`（VERSION + CHANGELOG + CR 闭环）作为制品定义的版本治理纪律。

## 五、目标数据模型

### 5.1 新 schema：`databases/asset_core/schemas/018_knowledge_product.sql`

落在**按域路由的 asset_core 库**（D6 的直接结论）。

| 表 | 作用 | 关键约束 |
|---|---|---|
| `kp_products` | 制品身份 | `product_id`、`product_type`（registry 类型）、`purpose`、`owner`、`lifecycle_status`、`current_draft_revision`、`released_revision`。**不带 domain 外键**（51号批次3：制品身份去 domain），归属由 owner 表达 |
| `kp_product_definitions` | 制品定义修订 | 字段定义 / 对象规则 / 人工样例 / 试用问题 / 资料范围；每次改动一个新 `definition_revision` |
| `kp_scope_items` | 资料范围 | 指向 `asset_document_snapshots`，可选 `allowed_sections`；**票据校验的唯一依据** |
| `kp_revisions` | 草稿/发布修订 | `revision_no`、`status ∈ {draft, in_review, published, superseded}`；发布即冻结 |
| `kp_objects` | 对象 md 索引 | `PK(product_id, object_id, revision_no)`；`type`/`layer`/`scope`/`name`/`frontmatter_json`/`storage_object_id`（正文在 MinIO） |
| `kp_edges` | 对象间边 | `(from_object_id, revision_no, relation, to_object_id)`；`to` 允许指向尚不存在的 ID（悬挂边，报告但不阻断） |
| `kp_evidence` | 对象/字段级证据 | FK → `asset_document_snapshots` + `asset_raw_segments`；**CHECK 非空**（照搬 ontology 的出处强约束） |
| `kp_creation_instances` | 制作实例 | 绑定 product + definition_revision + 起始 draft_revision；`harness_session_id`、状态机、事件补读位置与去重键 |
| `kp_task_tickets` | 任务票据 | 短期、可撤销、绑定实例与资料范围；签发/拒绝入审计，页面与日志脱敏 |
| `kp_submissions` | 提交回执 | `submission_id` 幂等键、`based_on_draft_revision`、接受/冲突/拒绝计数 |
| `kp_reviews` | 审核记录 | 审核人、结论、逐对象意见；驳回意见是 D8 续跑的输入 |

### 5.2 存储分工

```text
PG (asset_core, 按域路由)          MinIO (asset_storage_objects)
├─ kp_objects  索引/frontmatter ──ref──► 对象 md 正文
├─ kp_edges    边
├─ kp_evidence 证据锚点 ──FK──► asset_document_snapshots / asset_raw_segments
└─ 制作实例/票据/提交/审核
```

正文永远不进 PG 大字段；`asset_storage_object_refs` 记引用，制品修订退役时按引用计数回收。

### 5.3 逻辑 ID（提案，待确认）

newsfc 是 `{nf}@{Type}@{local}` 三段（nf=网元，隔离位）与 `{Type}@{slug}` 两段（跨网元）。CoreMasterKB 无 nf 概念，**用制品 slug 顶替隔离位**：

| scope | 形态 | 例 |
|---|---|---|
| `product`（制品内对象） | `{product}@{Type}@{local}` | `spec-ne8000@DataProduct@NE8000-M8` |
| `cross`（跨制品共享） | `{Type}@{slug}` | `OntologyModule@site-device` |

沿用 newsfc 的两条铁律：**版本不进 ID**（只在 frontmatter 和修订号里）；**文件名 = 完整逻辑 ID**（保留空格）。

**复合行标识**（样品验证结论 F4）：行标识常常是多个字段（如「型号 + 产品版本」），local 段只能是一个字符串。registry 增加 `local_from: [model, product_version]`，由**平台按序拼接并校验唯一**，不让 Agent 自己拼——Agent 拼会出现同一行两种写法。

### 5.4 registry 初始类型（按 48 号 §3）

```yaml
object_types:
  OntologyModule:    { layer: Ontology,  scope: cross,   id_segments: 2, ... }
  DomainFactSet:     { layer: Fact,      scope: product, id_segments: 3, ... }
  DataProduct:       { layer: Data,      scope: product, id_segments: 3, ... }
  RulePackage:       { layer: Rule,      scope: product, id_segments: 3, ... }
  ScenarioPackage:   { layer: Scenario,  scope: cross,   id_segments: 2, ... }
  MethodPackage:     { layer: Method,    scope: cross,   id_segments: 2, ... }
```

首期只需把规格矩阵跑通（50 号试点），其余占位。

**一个制品同时产出两类对象**（样品验证结论 F1）：上表把这六类列成并列类型，实际使用中，一个规格矩阵制品会同时产出——

| 对象 | scope | 作用 |
|---|---|---|
| `DataProduct@spec-ne8000` | cross（2 段） | 制品对外的身份与入口，正文是整张表。**别的制品引用的是它** |
| `spec-ne8000@DomainFactSet@{型号} {版本}` | product（3 段） | 一行一张对象卡。**逐字段回源查的是它** |

所以 registry 的类型不是「制品类型」，是「对象类型」；`kp_products.product_type` 与对象的 `type` 是两个概念。

**字段与证据必须结构化进 frontmatter**（样品验证结论 F2）：逐字段回源要求每个值单独挂证据，md 正文的表格做不到机器校验。对象卡的 `fields` 是 frontmatter 里的结构化块（值 + 单位 + 证据数组），正文表格只是它的渲染。`submit_creation_result` 校验 `fields`，不碰正文。

## 六、模块边界与接口

### 6.1 四个模块（50 号 §4.3，落到 knowledge_mining）

```text
knowledge_mining/mining/
```

同进程、同数据库。这是责任边界，不是微服务。

### 6.2 制作 MCP 的四个工具

> **勘误（2026-09-20，P2 开工时核对源码）**：本节初稿有两处错。一是把 `mcp_server`
> 的工具清单写成 README 里的「九件套」——那份描述已过时，2026-08-31 合并后**现存
> 只有三个工具**：`search_knowledge` / `get_knowledge` / `upload_document`
> （`mcp_server/identity.py` 的 `TOOL_NAMES`）。二是据此推出「工具名撞名、需要新增
> 一种 Identity 类型」——**没有撞名**：50 号要的两个读工具，名字与现存的完全一致。

50 号 §3.2 的设计是**服务身份 + 票据参数**，不是「票据身份」：

- **服务身份** = DSH 固定配置的那把 MCP 钥匙，走现有 `require_identity`；
- **任务票据** = 每次工具调用传的 `task_ticket` 参数，决定这一次能读什么、能写到哪个草稿。

票据做参数而不是做身份，是因为它短期、可撤销、绑定到具体制作实例——做成身份就得
让 DSH 每接一个任务轮换一次 MCP 钥匙，而 50 号明确要求「不为每个制品改变 MCP 地址、
工具清单或重新部署 Harness」。

| 工具 | 归属 | 说明 |
|---|---|---|
| `get_creation_context` | 新增 | 本次制品目标、字段定义、资料清单、样例、当前草稿摘要、待确认项、输出结构 |
| `submit_creation_result` | 新增 | 校验后写入绑定草稿，或返回结构/来源/并发冲突错误 |
| `search_knowledge` | **复用现有** | 带 `task_ticket` 时检索范围收窄到票据允许的快照 |
| `get_knowledge` | **复用现有** | 同上；并随每段内容返回 `segment_id`，供 Agent 原样带回作证据 |

这样 DSH 只配一个 MCP 地址和一套固定工具清单，证据检索不写第二套实现，收窄逻辑
集中在票据解析一处。

### 6.3 四处 newsfc 规则要改，不能照抄

1. **边索引口径不一致**：newsfc 的 `index` 只扫 `## 边` 段建边，但 `get_domains` 的 `references` 又是全文扫 `[[ID]]`——同一份 md 两个口径。**移植统一为：全文扫 `[[ID]]` 建边，`## 边` 段只负责标注关系类型**（无标注的内联引用记为 `mentions`）。
2. **边必须按 (from, to, relation) 去重**（样品验证结论 F6）：统一成全文扫之后，同一目标常在正文内联和 `## 边` 各出现一次。样品实测不去重会从 22 条边虚增到 29 条。newsfc 的 `PK(from_id, from_version, relation, "to")` 天然去重，移植时别把这个主键改窄。
3. **跨制品共享对象不做反向回填**（样品验证结论 F5）：newsfc 要求「被引用对象在 `## 边` 反向回填 `被引用于`」。这条在这里**不成立**——样品里一个 `OntologyModule` 被 5 张对象卡引用，逐条回填会让它的 `## 边` 随引用方无限增长，而引用方属于别的制品、别的修订，对它并无写权限。newsfc 能这么做是因为它是单一资产库、全量重建索引。**改为：正向边由源对象 md 承载，反向边由 `kp_edges` 索引查询提供，不写回 md。**
4. **`_index.md` 复用库有规则无载体**：newsfc Task 层 SKILL 反复引用一个不存在的复用库。移植时不引入「复用判定」这条规则，或先建载体再写规则。

另外 newsfc 的 CHANGELOG 存在两个 `0.12.0`、各层状态表描述偏旧——演进机制的纪律要在移植时真正执行，不是把文档抄过来。

**已交付**（2026-09-20）：

在此之前制品体系是**只写不读**——能做、能审、能发布，但没有任何人或 Agent 能读到

|---|---|
| `consume.py` | 护栏与排序纯逻辑：批量上限 50、响应上限 2MB、terms 规范化（NFKC+casefold）、命中排序（命中词数→元数据等级→type/id）、零结果恢复码 |
| `consume_service.py` | `catalog` / `outline` / `fetch` / `search`。**只认已发布修订**——草稿对消费方不可见 |
| 仓储 | `list_published_products` / `get_published_objects` / `list_published_objects`——JOIN 到 `kp_products.released_revision` 就是「对外服务的那一份」 |
| 接口 | `/api/published-products/*`（前端面）+ `/api/product-consume/*`（工具面，internal-only） |
| MCP 工具 | `search_products` / `get_product`。与证据三件套**正交**：那三个查原始资料，这两个查已发布结论 |

照搬 newsfc 的四条调用纪律（都已在 2 万+ 对象上跑过）：

1. **snippet 不是权威依据**——选定候选后必须 `get_product` 取原文；工具描述里写死这条。
2. **单项失败不阻断整批**——一个 ID 不存在不该让另外九个也白取。
3. **响应总量超限整单失败并指引分批**——宁可多跑一轮，也别塞爆 Agent 的上下文。
4. **零结果给恢复码**而不是空数组：`USE_MATCH_ANY` / `REMOVE_OR_REPHRASE_TERM` / `RELAX_FILTERS`，外加 `term_counts` 指出是哪个词没救。

**MCP instructions 增了决策树**（46号 §6 的消费路径）：先 `search_products`，零结果或
候选不贴题再回 `search_knowledge`。两族可混用——制品的 md 里带
`document_id`/`snapshot_id`/`segment_id`，能直接拿去 `get_knowledge` 回原文核对。

- 消费工具**默认开放**（进 `TOOL_NAMES`），不像制作工具那样需显式开启。理由：它们
  只读、按钥匙绑定域收窄，而 P6 的全部意义就是让制品被用起来——做成需显式开启等于
  默认没人能消费。代价是每把存量钥匙的工具清单多两个。
- 因此改了 `test_tool_surface.py` 里那条锁死「只有三件套」的护栏。护栏没有放松，
  改成锁新的精确成员，并补锁「制作工具不得进默认集」与「两侧清单一一对应」。

**搜索覆盖面的边界**：搜对象 ID、名称、frontmatter 的结构化 `fields`（事实型制品真正
的数据值都在那里），**不搜正文散文**——正文在对象存储里，搜它要另建全文索引。对
规格表/事实集够用，对 Wiki/专题页不够。这条写进了工具描述，别让 Agent 以为搜不到
就是没有。

### 平台侧 P7：制品运营（不等 DSH）

**已交付**（2026-09-20）。48号 §八「资料变了、用错了，能继续更新」——首期只做
「提醒 + 人工触发更新 + 差异确认」，不建全自动知识演进系统。

| 能力 | 内容 |
|---|---|
| 定义修订 | 改定义 = **开新的一版**，不是原地改。旧定义留着（已发布修订指向它）；未给的部分从当前定义继承——改字段定义不该顺手把资料范围清空 |
| 撤票联动 | 改完定义**立即撤销该制品在用票据**。Agent 手里的旧票据绑定旧定义修订，按旧范围继续提交就等于绕过了这次改动（50号 §7.1）。两件事在路由层组合，不让载体层反过来依赖制作面 |
| 报告问题 | `kp_issues`：谁、在做什么任务、用哪一版、哪里不对、修正依据。处置记的是**方向**（改资料/改定义/改内容/改 Agent 用法）而不是一个「已修复」布尔——区分开才知道下次该防哪一类 |
| 影响分析 | `impact.py`。**不需要新表**：文档→制品的关系已在 `kp_evidence`（每字段记了 snapshot_id），制品→制品在 `kp_edges`。这里只是反着查 |

按 48号 分两类变化，因为处置方式不同：

| 变化 | 表达 | 处置 |
|---|---|---|
| 新资料/新版本出现 | `superseded` | 提示复核，旧依据是否仍适用由责任人按业务范围判断 |
| 内容删除/权限收回/明确失效 | `revoked`（blocking）/ `deprecated` | 「不能只挂待办继续暴露」 |

**「不能只挂待办」这条落在消费面**：`outline` 返回 `source_status`（`ok`/`stale`/
`blocked`/`unknown`）。只让负责人看见告警仍然是挂待办，所以消费方在决定依赖这个
制品**之前**就该看到它引用的资料现在是什么状态。查不到快照现状时如实报 `blocked`
而不是假装健康。

**没有做自动下架**：`blocked` 是个显式标记，不是自动撤销发布。是否下架是治理决定，
不该由一条 GC 规则替负责人做。这条留给你定。

**顺带修掉一个 P1 缺陷**：`write_draft_revision` 原先取 `MAX(definition_revision)
FROM kp_revisions`——那是既有修订里的最大值，不是当前最新定义。于是负责人改完定义
之后，下一个草稿仍按旧定义走，「改定义」对制作毫无效果。改为从
`kp_product_definitions` 取。

Schema `021_knowledge_product_ops.sql`（只加 `kp_issues` 一张表）。

### R6 实测结论（2026-09-20，一次性测试库）

布置：两个「废弃满 30 天」的快照，A 被一个已发布制品的证据引用，B 无人引用。
直接调真实的 `PurgeService.reclaim_deprecated_snapshots(older_than_days=7)`：

```
GC 整轮抛出 → ForeignKeyViolation（约束 kp_evidence_snapshot_id_fkey）
跑完后仍存活: A(被引用) B(无引用)   ← B 也没被回收
```

**不是「这一个快照删不掉」，是「整轮 GC 死掉」。** 原因在
`reclaim_deprecated_snapshots` 的结构：它逐个快照循环，异常直接穿出 for 循环，
后面的快照全部不再处理，`_reclaim_objects_if_orphaned` 也不执行。异常最终被
`app.py` 的 GC 循环捕获、记一条 warning、睡 24 小时——**第二天同一个快照还在，
同样死掉**。

一个好消息：`self._pool.connection()` 是事务上下文，失败前已删的 links /
build 选片行会回滚，**没有数据损坏**。

触发条件不是边缘情况，是正常生命周期：只要有人发布了引用某快照的制品，而该快照
后来因为换范式/内容更新被废弃，就会触发。
