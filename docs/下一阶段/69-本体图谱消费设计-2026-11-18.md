# 本体图谱消费设计（MCP 图查询 + 检索融合 + 抽取溯源，69号）

> 承接 67号（本体管理 MVP）与 68号（图谱可视化）。两期之后图谱已经「能建、能看」，
> 但消费者只有建它的那个人工界面——这是精装孤岛。本期把图谱接进**消费面**：
> Agent 能查（MCP 工具）、检索能带出（面板融合）、来源能回溯（溯源列）。
>
> 立场（用户已拍板）：**先消费后建模**。对象↔制品/文档的 refs 软引用层延后——
> 先验证消费真的发生、问法长什么样，再决定要不要建关联模型；本期不做任何硬关联。
>
> 2026-11-18 评审修订（对照 1.1.49 合并后代码核实）：迁移号 022→023（022 已被
> 本体建表占用）；文档表名 kb_documents→asset_documents（purge 有物理删除，
> 不加 FK 的理由改写）；发版号 1.1.38→1.1.50；对象响应增加 source_kb_id；
> MCP 工具开关与记账口径改定；P1 并行搜索补代际防护。

## 二、顺手项：抽取溯源 source_document_id

### 2.1 动机与现状

`semantic_objects.source` 只是通道标签（`manual`/`import`/`extract`，CHECK 约束）——
AI 抽出的对象是「无来源的断言」，不知道出自哪篇文档。抽取向导装配源文本时已经
校验过 `{kb_id, document_id}`（`_kb_document_text`：KB 属本域、文档已挖掘），
确认落库时把这个 document_id 顺手记下即可。

### 2.2 DDL（`databases/kb/schemas/023_semantic_object_provenance.sql` + 同名迁移）

> 编号 023：022 已被本体六表占用（1.1.49 合并 upstream 时 021_kb_workspaces
> 占 021，本体建表 021→022 改号让位）。

```sql
ALTER TABLE semantic_objects
    ADD COLUMN IF NOT EXISTS source_document_id TEXT;
CREATE INDEX IF NOT EXISTS idx_semantic_objects_source_doc
    ON semantic_objects(source_document_id)
    WHERE source_document_id IS NOT NULL;
```

不加外键，两条理由：①文档表是 asset_documents（库里**没有** kb_documents 表），
清库/purge 路径对它有**物理 DELETE**（purge_service 同事务删行）——真加 FK 会被
本体对象的存量引用卡死清库；②读取侧反正要处理「文档已删」的展示降级，FK 无
增量价值，只增加本体六表对外键面的耦合（022 目前只引用 kb_users）。

### 2.3 写入路径（instantiate_batch 单点）

- `InstantiateIn` 加 `source_document_id: str | None = None`。
- 校验：仅当 `source='extract'` 时接受该字段，其余通道传了 → 422；**不校验文档存在性**
  ——溯源是记录不是约束（文档后续软删不应阻断读取，更不该阻断历史回放）。
- 服务端不重验 KB 归属：候选结果本身出自本库抽取流程，越域伪造最多写一个无效
  引用，读取侧降级兜底。
- `db_ontology` 对象 INSERT 共三处（create_object 单建 / batch_insert_objects
  导入 / instantiate_batch 实例化），本期**只改 instantiate_batch 一处**加列；
  另两处是显式列清单，不写新列即缺省 NULL，不必动。
- **前端必传点**：`OntologyExtractWizard.commitInstantiate` 的 payload 在
  `sourceKind==='kb_document'` 时带 `source_document_id: documentId`；
  text/file 两种源不带（无文档可溯）。
- 历史存量对象不回填（无据可查）。

### 2.4 读取与展示

- `GET /objects` 列表、`GET /objects/{id}`、图谱抽屉共用的对象响应加**三个**键：
  `source_document_id`、`source_document_name`、`source_kb_id`（同一条
  LEFT JOIN asset_documents 取 document_name/kb_id，**滤 deleted_at IS NULL**）。
  source_kb_id 必须带：文档预览路由是路径参数 `kb/:kbId/doc/:docId`，展示时刻
  前端只有 document_id 拼不出链接——「向导落库前已知」帮不了列表页的点击。
  软删/物理删/查无统一降级：name 与 kb_id 为 null，id 仍在（软删恢复后自动回显）。
- 对象 Tab「来源」列升级：extract 且有文档 → 「AI 抽取 · {文档名}」，文档名可点，
  跳既有文档预览路由（kb-doc-preview，params={kbId: source_kb_id,
  docId: source_document_id}）；name 为 null → 「AI 抽取 ·
  来源文档已不可访问」纯文本。
- 图谱抽屉同口径展示一行。

## 三、P0：MCP 图查询工具族

### 3.1 工具清单（mcp_server `@mcp.tool()` 三件套，全部只读）

| 工具 | 参数 | 返回 | 后端复用 |
|---|---|---|---|
| `list_ontology_libraries` | —（域来自密钥绑定） | 域内库清单：id/name/description/本体数/对象数/关系数 | `list_libraries(domain=key.domain)`（counts 已在响应里） |
| `query_ontology_graph` | `library_id`；可选 `ontology_names: str[]`（名称比 id 对 Agent 友好）、`limit≤2000` | 68号 §2.2 载荷（nodes/edges/total_objects/truncated）**外加** ontologies 摘要键（id/name 对应表，Agent 复述用） | `get_library_graph` + `get_library_schema` **两次调用**：图载荷没有 ontologies 键、SQL 过滤只认 ontology_ids——schema 的 {ontologies, relations} 既做对应表也做名称→id 解析（库内名唯一有 UNIQUE(library_id,name) 兜底，未知名 422 列出合法名） |
| `get_semantic_neighbors` | `object_id` | 对象卡（名称/本体/属性）+ 一度邻接 `{outgoing[], incoming[]}`（边带 relation_name + 对端对象摘要） | `get_object` + `get_object_neighbors` 原样 |

工具 docstring 里给核心域示例问法（网元/设备/承载/作用于），引导 Agent 正确调用。

### 3.2 Agent 验收脚本（三问）

```
Q: 核心网域有哪些本体库？           → list_ontology_libraries
Q: 画「核心网知识本体」的实例图，    → query_ontology_graph(ontology_names=[网元, 业务])
   只要网元和业务
Q: AMF 周边关联了什么？             → get_semantic_neighbors(sobj_AMF)
                                     → 出边：承载→SMF…；入边：作用于←网络切片…
```

### 3.3 内部端点（mining 新文件 `routes/mcp_ontology.py`，前缀同 `/api/kb/mcp-tools`）

| 端点 | body | 防线（在 `_require_internal` 之后） |
|---|---|---|
| `POST /ontology/list-libraries` | username, key_id | `_key_scope`（钥匙存在/本人/active）→ 用户是 key.domain 域成员或站点管理员（service `_require_read`） |
| `POST /ontology/library-graph` | username, key_id, library_id, ontology_names?, limit? | 同上，另加 **library.domain == key.domain**（钥匙域收口，不匹配 → 404 不泄露存在性） |
| `POST /ontology/object-neighbors` | username, key_id, object_id | 同上（对象→库→域校验链） |

- 授权模型一句话：**钥匙的域 × 用户的域成员身份**。与 kb 族 `key_open_kb_ids`
  （钥匙按库开放，细粒度）刻意不同：本体库没有按库开放开关，域内成员即读——
  对齐网页端 `_require_read`（本体是域级类型资产，粒度天生粗于知识库）。
- 实现形态：路由把 username 解析成 `{id, site_role}` 的 user dict，直接调
  `OntologyService` 既有方法（图/邻接/清单的读校验服务层已齐），路由层只补
  钥匙域收口一行。注册顺序在动态 `/api/kb/{kb_id}` 之前（静态前缀，同 mcp_tools）。
- mcp_server 侧：`tools.py` 加三个 `_post` 族函数（复用 X-Internal-Auth 面），
  `server.py` 注册三个 `@mcp.tool()`；身份走 `_identity()`，域不显式传（密钥绑定）。
- 审计：mining 侧与 kb 族读取端点同口径不记账；但 mcp_server 中间件对
  `@mcp.tool()` 每次调用都写 access_record（pending→complete 落
  /api/internal/retrieval-records）——三新工具注册后**自动有账**，口径定为
  「沿用中间件默认」，原「计量预留」实际免费到手。
- 工具开关：三新工具加入 `Identity.TOOL_NAMES`（现三件套）受钥匙 open_tools
  开关管，钥匙未配置开关时默认全放行——与现有工具同一语义，不另造口径
  （实现时核对中间件对空 open_tools 的现行为，空=全放行则零改动）。

## 四、P1：检索面板融合与图谱跳转

### 4.1 域级对象搜索端点（mining）

```
GET /ontology/search/objects?domain=…&q=…&limit=20
```

- 权限：`_require_read`（域成员），domain 显式参数——同 `list_libraries` 模式。
- 匹配：对象名 ILIKE `%q%`（不扫 attributes_json，见 §1.2）；跨库查域内全部库，
  按库分组；`limit` 默认/上限 20，超出 `truncated: true`。
- 响应：`{truncated, hits: [{library_id, library_name, ontology_name,
  object_id, object_name, degree, source_document_id?}]}`——degree 为该对象
  一度邻接边数（出+入，COUNT 子查询），卡片上「12 关联」用。

### 4.2 KbSearchPanel 卡片组

- 触发：范式检索执行时（q 非空）**并行**发对象搜索，不阻塞证据结果渲染；
  域取 domainStore 当前域。对象搜索**并入主检索的 searchGeneration 代际快照**
  （快速连搜时过期响应一并丢弃，防旧卡组覆盖新结果）；请求失败静默隐藏卡组，
  不弹错误条、不影响证据列。
- 渲染：结果列顶部「语义对象（域级本体库）」卡组——底色用 `--kb-accent-soft`
  （teal 即全站主强调色 --kb-accent，与证据卡的靛蓝徽标形成区分，不引入新色）；
  每卡：对象名 + 本体名 tag + 所属库名 + 关联数。无命中整组隐藏，不占位。
- 卡片组标题带「域级」标注：检索面板是**库**上下文，对象是**域**上下文，
  口径不同必须写明，避免用户误以为是本库检索命中。

### 4.3 跳转图谱聚焦

- 卡片点击 → `ontology-library-detail?tab=graph&focus=<object_id>`。detail 页
  activeTab 现为纯本地状态，setup 一次性读 route.query.tab（同 KbDetailView
  先例）；GraphTab 是 lazy 挂载，focus 经 prop 传入、等图渲染完成后消费。
- GraphTab 支持 focus：`graph.focusElement` 视口居中（G6 5.1 现成 API）+
  **新建** focus 高亮态——现状没有点击选中态（node:click 直接开抽屉），这是
  新能力不是复用：最小实现=目标节点描边强调，**不**连带开抽屉；节点被本体
  过滤开关排除 → 自动清过滤再定位。
- 库超 2000 截断未含该节点 → 兜底：带 `ontology_ids=[该对象的本体]` 重拉一次
  图再定位（getLibraryGraph 本就支持参数，前端目前没传）；仍未命中 → 提示
  「对象存在，当前图已截断」。
- focus 消费后清掉 query 参数：`router.replace({ query: { ...route.query 去
  focus 键 } })`（项目无清参先例、属新模式；避免刷新重复跳 tab）。

## 七、拍板项（默认按推荐走，有异议告诉我）

1. **MCP 工具=独立三件套**，不塞 `get_knowledge` 视图族、不做对象 ref（`obj_` 前缀）——
   查询型工具直呼直用；ref 化等 Agent 真需要从检索结果跳图谱再说（P1b）。
2. **授权=钥匙域 × 域成员**，本体库无按库开放开关——与 kb 的钥匙开放库刻意不同粒度。
3. **source_document_id 不加 FK**——purge 对 asset_documents 有物理删除，FK 会
   卡死清库；读取侧降级（name/kb_id → null）反正要做，FK 无增量价值。
4. **抽取确认必传来源文档**（kb_document 源）；text/file 源与历史存量不溯、不回填。
5. **融合入口=库检索面板卡组**（带域级标注），不动 `search_knowledge`、不动全局搜索。
6. **P1 只按对象名匹配**（不扫属性值），命中上限 20。
7. **MCP 三新工具加入 TOOL_NAMES 受钥匙 open_tools 开关管**（未配置开关=默认
   全放行）；记账沿用 mcp_server 中间件默认——`@mcp.tool()` 每次调用自动写
   access_record，不做额外计量预留。
