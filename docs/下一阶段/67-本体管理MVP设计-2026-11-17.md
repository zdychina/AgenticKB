# 本体管理 MVP 设计（本体库 / 本体 / 语义对象 / 批量导入 / AI 辅助实例化）

> 编号：67号
> 版本：V1.0
> 日期：2026-11-17
> 定位：全新功能线——**人工自定义本体**的管理：类型层（本体/属性/本体关系）+ 实例层（语义对象/语义关系），以及两条实例化加速通道（表格批量导入、AI 辅助抽取）。
> 范围声明：MVP = 本体库全生命周期 CRUD + 手工实例化 + 表格批量导入 + AI 辅助抽取（人工确认后落库）。图可视化、属性类型系统、本体继承、语义对象与 KB 资产的双向挂接全部不做，但表结构与流程为其预留接入口（§十四）。
> 讨论过程：2026-11-16/17 多轮逐概念过审（概念模型→图数据库类比对齐→属性形态与关系端点约束两项设计决策→删除保护矩阵→导入/抽取产品决策三次确认）。

## 一、范围

### 1.1 做什么（MVP 五大块）

1. **本体库**：域下创建（一域多库），管理员/域管理员专属；库内管理一切。
2. **本体（类型层）**：CRUD + 查询；本体上挂**属性定义**（名称 + 描述 + 排序，无类型系统，可增删改）。
3. **本体关系（类型层）**：命名有向边类型，绑定「源本体 → 目标本体」，库内名称唯一。
4. **语义对象 / 语义关系（实例层）**：按本体手工实例化（动态表单填属性值）；对象之间按本体关系建边，端点强校验。
5. **实例化加速**：
   - **表格批量导入**：CSV/XLSX → 表头映射到属性定义 → 逐行校验 → 全有或全无落库；
   - **AI 辅助抽取**：粘贴文本 / 上传 txt/md / 选择 KB 文档 → LLM 按本体 schema 抽取对象候选 + 关系建议 → 人工确认编辑 → 原子落库。

### 1.2 明确不做（MVP 边界）

| 不做 | 处理 |
|---|---|
| 属性类型系统（text/int/enum…） | 属性无类型，值 = 自由标量；演进路径见 §十四 |
| 属性必填 / 默认值 | 留空即不写键，详情按定义驱动展示为空 |
| 本体继承（子类/父类） | 本体平铺 |
| 本体/库的版本与草稿机制 | 编辑直接生效 |
| 图可视化（schema 图 / 实例图渲染） | 提供 `/schema` 与 `/neighbors` 数据端点，渲染二期做 |
| 语义对象挂接 KB 资产（chunk/实体/文档引用） | 语义对象独立存储；KB 文档仅作为 AI 抽取的**只读输入源** |
| 悬空宽容策略 | 删除保护全强 RESTRICT（§4.8） |
| 跨库引用 | 关系两端对象必须同库 |
| LLM 无人值守自动落库 | AI 产出仅为候选，必须人工确认 |

## 二、概念模型

### 2.1 术语表

| 术语 | 定义 | 编程类比 | 图数据库类比 |
|---|---|---|---|
| 本体库 (ontology library) | 域下的容器，本体管理的入口 | 工程 / 包 | 图数据库实例 |
| 本体 (ontology) | 人工定义的概念类型，挂属性定义 | 类 (class) | 节点类型 (label) |
| 属性定义 (attribute) | 本体上的自定义属性项：名称+描述+排序 | 类的字段声明 | 节点类型的属性键 |
| 本体关系 (ontology relation) | 命名有向边类型，绑定源/目标本体 | 类之间的关联 | 边类型 (relationship type) |
| 语义对象 (semantic object) | 某本体的实例，填属性值 | 对象 (instance) | 节点 (vertex) |
| 语义关系 (semantic relation) | 两个语义对象之间的边实例 | 对象引用 | 边 (edge) |

### 2.2 结构总览

```
域 (Domain)
 └── 本体库                          ← 站点管理员/域管理员创建；一域可多库
      ├─ 类型层（schema，人工定义）
      │    ├── 本体         ≈ 类 / 节点类型        CRUD + 查询
      │    │    └── 属性定义 ≈ 类的字段            无类型，可增删改
      │    └── 本体关系     ≈ 类的关联 / 边类型    源本体 → 目标本体，有向
      └─ 实例层（数据图）
           ├── 语义对象     ≈ 对象 / 图的节点      按本体创建，填属性值
           │    ├── 来源：手工表单 / 表格导入 / AI 抽取确认
           │    └── 创建入口：手工 §5.3 / 导入 §七 / AI §八
           └── 语义关系     ≈ 对象引用 / 图的边    按本体关系连接两个对象
```

### 2.3 两项已定设计决策

**决策一：属性 = 名称 + 描述，值 = 自由标量（无类型校验）。**
属性的全部语义就是"这个名字"；描述帮助人和 LLM 消费者理解含义；值放对象行 `attributes_json`（JSONB），创建/编辑时只接受标量（string/number/bool），不做类型校验。将来加类型/必填 = 属性定义表加列 + 应用层校验，不动存量数据。

**决策二：本体关系 = 命名有向边类型，绑定「源本体 → 目标本体」，创建边实例时强校验两端。**
关系天然定义在两个本体之上；强校验保证实例图永远合法（无悬空边、无跨类型乱连）；UI 上 schema 图直接渲染为「本体节点 + 箭头边」。同一对本体可定义多个关系；允许源 = 目标（自环类型，如「人 —认识→ 人」）；库内关系名唯一（下拉选择无歧义）。

## 四、数据模型设计

### 4.0 风格约定

对齐 `002_knowledge_bases.sql`：TEXT 主键（服务层生成，同 `_new_id`）、TEXT ISO 时间戳（`_utcnow`）、`created_by REFERENCES kb_users(id)`、幂等 `CREATE IF NOT EXISTS`、中文注释。表落各域分库（kb 表组）。

### 4.1 本体库

```sql
-- Ontology management: 本体库（域下容器，人工自定义本体的入口）。
-- domain 必须是 domain_registry.yaml 合法域（应用层校验）；删除为硬删，
-- 由应用层"库内有本体即拒绝"保护（§4.8），无资产引用故不做软删。
CREATE TABLE IF NOT EXISTS ontology_libraries (
    id          TEXT PRIMARY KEY,
    domain      TEXT NOT NULL,
    name        TEXT NOT NULL,
    description TEXT,
    created_by  TEXT NOT NULL REFERENCES kb_users(id),
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    UNIQUE (domain, name)                        -- 域内本体库名唯一
);
CREATE INDEX IF NOT EXISTS idx_ontology_libraries_domain ON ontology_libraries(domain);
```

### 4.2 本体（节点类型）

```sql
CREATE TABLE IF NOT EXISTS ontologies (
    id          TEXT PRIMARY KEY,
    library_id  TEXT NOT NULL REFERENCES ontology_libraries(id) ON DELETE CASCADE,
    name        TEXT NOT NULL,
    description TEXT,
    created_by  TEXT NOT NULL REFERENCES kb_users(id),
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    UNIQUE (library_id, name)                    -- 库内本体名唯一
);
CREATE INDEX IF NOT EXISTS idx_ontologies_library ON ontologies(library_id);
```

库删除被应用层"有本体即 409"拦截，CASCADE 只是最后防线，正常不可达。

### 4.3 属性定义

```sql
CREATE TABLE IF NOT EXISTS ontology_attributes (
    id          TEXT PRIMARY KEY,
    ontology_id TEXT NOT NULL REFERENCES ontologies(id) ON DELETE CASCADE,
    name        TEXT NOT NULL,
    description TEXT,
    sort_order  INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT NOT NULL,
    UNIQUE (ontology_id, name)                   -- 同一本体内属性名唯一
);
CREATE INDEX IF NOT EXISTS idx_ontology_attributes_ontology ON ontology_attributes(ontology_id);
```

### 4.4 本体关系（边类型）

```sql
CREATE TABLE IF NOT EXISTS ontology_relations (
    id                  TEXT PRIMARY KEY,
    library_id          TEXT NOT NULL REFERENCES ontology_libraries(id) ON DELETE CASCADE,
    name                TEXT NOT NULL,
    description         TEXT,
    source_ontology_id  TEXT NOT NULL REFERENCES ontologies(id),   -- 删本体应用层拦截
    target_ontology_id  TEXT NOT NULL REFERENCES ontologies(id),
    created_by          TEXT NOT NULL REFERENCES kb_users(id),
    created_at          TEXT NOT NULL,
    updated_at          TEXT NOT NULL,
    UNIQUE (library_id, name)                    -- 库内关系类型名唯一
);
-- 源=目标 允许（自环类型）；本体删除被"被关系引用即 409"保护，FK 裸 RESTRICT 兜底。
CREATE INDEX IF NOT EXISTS idx_ontology_relations_src ON ontology_relations(source_ontology_id);
CREATE INDEX IF NOT EXISTS idx_ontology_relations_tgt ON ontology_relations(target_ontology_id);
```

### 4.5 语义对象（图的节点）

```sql
CREATE TABLE IF NOT EXISTS semantic_objects (
    id              TEXT PRIMARY KEY,
    library_id      TEXT NOT NULL REFERENCES ontology_libraries(id) ON DELETE CASCADE,
    ontology_id     TEXT NOT NULL REFERENCES ontologies(id),          -- 删本体应用层拦截
    name            TEXT NOT NULL,
    attributes_json JSONB NOT NULL DEFAULT '{}'::jsonb,   -- 键=属性定义名，值=自由标量
    source          TEXT NOT NULL DEFAULT 'manual'
                    CHECK (source IN ('manual','import','extract')), -- 实例化通道溯源
    created_by      TEXT NOT NULL REFERENCES kb_users(id),
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL,
    UNIQUE (ontology_id, name)                   -- 同一本体下对象名唯一
);
CREATE INDEX IF NOT EXISTS idx_semantic_objects_library ON semantic_objects(library_id);
CREATE INDEX IF NOT EXISTS idx_semantic_objects_ontology ON semantic_objects(ontology_id);
```

`library_id` 为冗余列：库级列表查询走它，且与 `ontology_id` 的库归属在写入时由服务层保证一致。

### 4.6 语义关系（图的边）

```sql
CREATE TABLE IF NOT EXISTS semantic_relations (
    id                    TEXT PRIMARY KEY,
    library_id            TEXT NOT NULL REFERENCES ontology_libraries(id) ON DELETE CASCADE,
    ontology_relation_id  TEXT NOT NULL REFERENCES ontology_relations(id),  -- 删边类型应用层拦截
    source_object_id      TEXT NOT NULL REFERENCES semantic_objects(id),    -- 删对象应用层拦截
    target_object_id      TEXT NOT NULL REFERENCES semantic_objects(id),
    created_by            TEXT NOT NULL REFERENCES kb_users(id),
    created_at            TEXT NOT NULL,
    CONSTRAINT chk_semrel_no_self CHECK (source_object_id <> target_object_id),
    UNIQUE (ontology_relation_id, source_object_id, target_object_id)  -- 防重边
);
CREATE INDEX IF NOT EXISTS idx_semantic_relations_src ON semantic_relations(source_object_id);
CREATE INDEX IF NOT EXISTS idx_semantic_relations_tgt ON semantic_relations(target_object_id);
```

### 4.7 唯一性与约束汇总

| 约束 | 粒度 |
|---|---|
| 本体库名 | 域内唯一 `UNIQUE(domain, name)` |
| 本体名 / 本体关系名 / 属性名 | 库内 / 库内 / 本体内唯一 |
| 语义对象名 | **同一本体下**唯一（不同本体可同名） |
| 语义关系 | 同关系类型 + 同起终点不重复；禁止自指边 |
| 语义关系端点 | 应用层强校验：源对象属于关系类型的源本体，目标对象属于目标本体（§5.2） |

### 4.8 删除保护矩阵（全部强 RESTRICT）

应用层先查并返回友好 409（detail 带计数），FK 裸约束兜底：

| 删除操作 | 拒绝条件（409 `in_use`） |
|---|---|
| 本体库 | 库内存在任何本体 |
| 本体 | 存在语义对象，**或** 被任何本体关系引用（作源或目标） |
| 本体关系 | 存在任何语义关系实例 |
| 属性定义 | 不拒绝；**同事务**清理该本体全部对象 `attributes_json` 中的对应键 |
| 语义对象 | 参与任何语义关系（作源或目标）——需先手动清边 |
| 语义关系 | 总是允许 |

### 4.9 修改限制矩阵

| 修改操作 | 规则 |
|---|---|
| 本体改名/描述 | 总是允许（实例只存 id 外键，无名字冗余） |
| 属性定义改名 | **同事务**重命名该本体全部对象 `attributes_json` 的键（保留值）：`SET attributes_json = attributes_json - old \|\| jsonb_build_object(new, attributes_json->old)` |
| 属性定义删除 | 见 §4.8：同事务清理存量键 |
| 本体关系改名/描述 | 总是允许 |
| 本体关系改端点（源/目标本体） | **有语义关系实例 → 拒绝（409）**，否则允许 |
| 语义对象改名/属性值 | 总是允许；改属性值走 §5.1 键校验 |
| 语义关系 | 创建后不可修改，只能删除重建（端点/类型即身份） |

## 五、核心业务规则

### 5.1 属性定义与属性值

- 属性定义 = `{name, description?, sort_order}`；排序序号供 UI 稳定展示，创建时默认追加到末尾（max+1）。
- 对象创建/编辑时 `attributes` 请求体的键必须 **⊆ 该本体当前属性定义名集合**，未知键 → 400 `unknown_attribute`（detail 列出未知键名）。
- 值必须是 JSON 标量（string / number / boolean），嵌套对象/数组 → 400 `invalid_attribute_value`。
- 留空的属性**不写键**（不是空字符串）；详情返回由属性定义驱动对齐：定义了但对象没填 → 显示为空。
- 本体后补的属性对旧对象天然显示为空，编辑补填即可。

### 5.2 本体关系与语义关系

- 创建本体关系时：源/目标本体必须属于同一库（path 参数的库），否则 400。
- 创建语义关系时（单条或批量 instantiate 同规则）：
  1. `ontology_relation`、源对象、目标对象三者必须同库；
  2. 源对象.`ontology_id` == 关系.`source_ontology_id`，目标对象.`ontology_id` == 关系.`target_ontology_id`，否则 400 `endpoint_mismatch`（detail 说明期望与实际）；
  3. 源 ≠ 目标对象；重复边 → 409 `duplicate`。

### 5.3 手工实例化机制（动态表单）

以「药品」本体（属性：适应症/用法用量/禁忌）实例化「阿司匹林」为例：

```
① 对象 Tab 点「创建对象」选定本体
② 前端 GET /ontologies/{id} 拿属性定义列表（按 sort_order）
③ 动态渲染表单：对象名 + 每属性一个自由输入框（描述作 placeholder）；可留空
④ POST /ontologies/{id}/objects {name, attributes}
⑤ 服务层校验（§5.1 键集合 + 标量 + 库内同本体重名 409）
⑥ 落库 semantic_objects（source='manual'）
```

编辑实例同理；批量导入落库 `source='import'`；AI 确认落库 `source='extract'`（§6.8）。

## 六、API 设计

### 6.1 通用约定

- 前缀：`/api/kb/ontology`（`APIRouter(prefix="/api/kb/ontology", tags=["kb-ontology"])`，注册于 app.py include 链）。
- 鉴权：网关注入的 `X-KB-User` + `X-Internal-Auth` → `current_user`（kb/auth.py 现有依赖）。
- 权限：**写操作**（POST/PUT/DELETE，含导入与抽取提交）= `can_manage_domain`（site admin OR domain admin，kb/db.py:775）；**读操作** = site admin 或 `user_domains` 绑定该域。库的域归属从库行取，入口统一校验，防跨域越权。
- 错误映射（对齐 kbs.py `_map_error` 模式，service 层抛类型化异常）：

| service 异常 | HTTP | 场景 |
|---|---|---|
| `NotFound` | 404 | 资源不存在/跨域不可见 |
| `Forbidden` | 403 | 非域成员读 / 非域管理员写 |
| `Duplicate` | 409 | 各级重名、重复边 |
| `InUse` | 409 | 删除保护/改端点保护（detail 带计数） |
| `InvalidDomain` | 400 | domain 非法 |
| `InvalidName` | 400 | 名称非法（空/超长/含非法字符） |
| `UnknownAttribute` / `InvalidAttributeValue` | 400 | §5.1 |
| `EndpointMismatch` | 400 | §5.2 |
| `ValidationReport` | 422 | 批量导入逐行错误报告（§7.4） |

- 分页：`?limit=&offset=`（默认 limit=50, offset=0），响应 `{items, total}`。
- 时间：ISO 字符串，同现有 kb 表。

### 6.2 本体库

| 方法 & 路径 | 说明 | 权限 |
|---|---|---|
| `POST /libraries` | 建库 | 域管理员 |
| `GET /libraries` | 列表（当前用户在当前域可见的库；`?q=` 名称模糊） | 域成员 |
| `GET /libraries/{id}` | 详情（带统计：本体数/对象数/关系实例数） | 域成员 |
| `PUT /libraries/{id}` | 改名/描述 | 域管理员 |
| `DELETE /libraries/{id}` | 删（有本体 409） | 域管理员 |

{ "domain": "cloud_core_network", "name": "核心网设备本体库", "description": "..." }
// 响应 201
{ "id": "ol_xxx", "domain": "cloud_core_network", "name": "核心网设备本体库",

```

### 6.3 本体与属性

| 方法 & 路径 | 说明 | 权限 |
|---|---|---|
| `POST /libraries/{id}/ontologies` | 建本体（可同时带初始属性列表） | 域管理员 |
| `GET /libraries/{id}/ontologies` | 本体列表（带属性数/对象数/关系引用数） | 域成员 |

| `DELETE /ontologies/{id}` | 删（有对象或被关系引用 409，detail 分别给计数） | 域管理员 |

| `PUT /attributes/{id}` | 改属性（改名触发 §4.9 键迁移） | 域管理员 |
| `DELETE /attributes/{id}` | 删属性（同事务清理存量键） | 域管理员 |

{ "name": "药品", "description": "域内收录的药品",

    { "name": "适应症", "description": "该药品适用的症状或疾病" },

### 6.8 批量实例化（AI 确认落库共用）

```
POST /libraries/{id}/instantiate
```

单事务落库「一批对象 + 一批关系」，**全有或全无**。AI 抽取确认页提交此端点；前端亦可复用它做任何批量创建。权限：域管理员。

```json
// 请求
{
  "ontology_id": "ont_xxx",                  // 本批新对象统一归属的本体
  "source": "extract",                       // manual|import|extract（import 由导入端点自己落库，不走这里）
  "objects": [                               // ≥1
    { "name": "阿司匹林", "attributes": { "适应症": "..." } }
  ],
  "relations": [                             // 可空；source/target 用 objects 序号或已有对象 id
    { "ontology_relation_id": "orel_xxx", "source_index": 0, "target_object_id": "sobj_yyy" }
  ]
}
```

- `source_index` 指向本批 `objects` 数组下标；`target_object_id` 指库内已有对象——关系两端可任意组合「新/已有」，但必须满足 §5.2 全部校验（同库、端点本体匹配、无重边）。
- 任一校验失败 → 整批 422 `ValidationReport`（带每项错误定位），不落任何数据。
- 成功 → 201，返回创建的对象/关系 id 列表。

## 七、批量导入设计（表格 → 语义对象）

### 7.1 交互流程（三步向导，对齐制品导入向导先例）

```
① 选文件        el-upload（.csv/.xlsx）+「首行为表头」勾选
② 列映射        表格列 → 对象名列（必选一个）+ 各属性列（可多选映射到属性定义）
③ 校验与导入    提交映射 → 后端全量逐行校验 → 有错：逐行错误报告（可下载，修正后重来）
                              → 无错：显示"将导入 N 个对象" → 确认 → 落库
```

### 7.2 后端处理（两步式 + preview token，对齐 artifact_import_service 模式）

**Step 1 上传解析** `POST /ontologies/{id}/objects/import/upload`（multipart）

- 文件约束：`.csv` / `.xlsx`；≤10MB；≤5000 数据行（超出 400）。
- 解析：xlsx 走 `openpyxl.load_workbook(read_only=True)`（经 `anyio.to_thread` 移出事件循环，对齐 artifacts.py:524 先例）；csv 走 `csv.DictReader`（utf-8-sig 容忍 BOM，对齐 user_import_service 先例）。
- 解析结果存**进程内存缓存**（token → parsed，1h 过期，LRU 上限与制品导入一致）；返回：

```json
{ "import_token": "imp_xxx", "row_count": 328,
  "columns": [{"name": "药品名称", "sample": "阿司匹林"}, ...],
  "preview_rows": [ { "药品名称": "阿司匹林", "适应症": "...", ... }, ... ],   // 前 20 行
  "detected_mapping": { "name_column": "药品名称",
                        "attribute_columns": { "适应症": "适应症", "用法用量": "用法用量" } } }
// detected_mapping：列名与属性定义名精确匹配的自动预选，UI 可改
```

**Step 2 提交导入** `POST /ontologies/{id}/objects/import/commit`

```json
{ "import_token": "imp_xxx",
  "name_column": "药品名称",
  "attribute_columns": { "适应症": "适应症", "规格": "用法用量" } }   // 列名 → 属性定义名；未映射列忽略
```

- 校验与落库同事务：全部通过 → `executemany` 批量 INSERT（psycopg3 cursor.executemany，对齐 kb/db.py:3088 先例），`source='import'`；任一行错误 → **整批拒绝**（用户决策），返回 422 报告，**不落任何数据**。
- token 消费后失效（一次性）。

### 7.3 值转换规则（单元格 → 标量）

| 单元格 | 键处理 |
|---|---|
| 空单元格 / 纯空白 | 不写键（留空语义） |
| xlsx 数值单元格 | number |
| xlsx 布尔单元格 | boolean |
| 其余 | string，去除首尾空白 |

### 7.4 逐行校验规则与错误报告

| 校验 | 错误码 |
|---|---|
| 对象名列的值空/纯空白 | `empty_name` |
| 与库内已有对象重名（同本体） | `duplicate_existing`（detail 带已有对象名） |
| **同批内**重名 | `duplicate_in_batch` |
| 名称超长（>200 字符） | `invalid_name` |

```json
// 422 响应体
{ "detail": "3 行校验失败，整批未导入",
  "report": { "total_rows": 328, "valid_rows": 325, "error_rows": 3,
              "errors": [ {"row": 17, "code": "duplicate_existing", "message": "对象「阿司匹林」已存在"},
                          {"row": 42, "code": "empty_name", "message": "名称列为空"},
                          {"row": 205, "code": "duplicate_in_batch", "message": "与第 88 行重名"} ] } }
```

前端将 `errors` 渲染为表格并支持导出 CSV（纯前端生成，无后端依赖）。

## 八、AI 辅助实例化设计

### 8.1 交互流程（向导）

```
① 选本体        目标 schema（抽取按此本体的属性定义产出候选）
② 选输入源      ○ 粘贴文本（≤20000 字符）
                ○ 上传 txt/md（前端 FileReader 读为文本，随 body 提交，无 multipart）
                ○ 选择 KB 文档：选知识库 → 选文档（复用现有 KB/文档列表 API）
                ☑ 同时建议对象间关系（默认勾选；产出新↔新、新↔已有 两类关系候选）
③ 抽取中        提交 → 返回 token → 前端轮询（进度提示，无阻塞）
④ 候选确认      对象候选表（可编辑名称/属性值、勾选排除、与库内重名标黄）
                关系候选表（源 → 关系名 → 目标，勾选排除，端点不匹配标红提示将无法落库）
⑤ 确认落库      POST /instantiate（§6.8），单事务全有或全无
```

### 8.2 KB 文档输入源（只读单向）

- 提交 `{kind: "kb_document", kb_id, document_id}`；后端校验该 KB/文档属于当前域且用户可见。
- 文本获取：复用 kb 文档管线的解析产物（该文档当前版本的纯文本分段），按序拼接，截断至 20000 字符；截断时响应带 `truncated: true` 提示。
- **边界**：KB 文档仅作为只读输入，语义对象不挂文档引用、不回写 KB——「独立管理」指产物独立。

### 8.3 异步任务链路（对齐 wiki_compile 的 GenerationClient 模式）

```
POST /libraries/{id}/extract {ontology_id, source, suggest_relations}
  → 校验 + 立即返回 {extract_token}            # 内存任务表：token → {status, result?, error?}，1h 过期
  → asyncio.create_task 后台执行：
      ① 组装 prompt（§8.4，含本体 schema、可选已有对象清单、源文本）
      ② LlmClient.execute(messages, expected_output_type="json_object")   # infra/llm_client.py 现有
      ③ 解析（剥 ```json 栅栏 → json.loads → 结构校验，对齐 llm_generation 先例的正则兜底）
      ④ 候选组装：重名检测（与库内已有对象）、关系端点预检（标红用）
      ⑤ 写回内存任务表 status=done
GET /libraries/{id}/extract/{token}   # 前端 2s 轮询
  → {status: pending|done|failed, candidates?, error?, warnings?}
```

- LLM 失败/解析失败 → `status=failed` + 原因文案；**不重试由用户决定重新提交**（llm_service 侧已有 task 级重试，execute 单次）。
- 内存任务表约束与制品导入 preview 缓存一致：单实例进程内有效、1h 过期、LRU 上限。多 worker 部署时轮询必须落回同一实例——与 artifacts preview token 同一既定约束，不新增机制。

### 8.4 Prompt 设计与版本冻结

独立常量模块 `ontology_extract_prompts.py`，**版本冻结铁律**（对齐 wiki_compile_prompts）：prompt 文本变更必须升版本号，用于结果缓存键与问题排查。

```python
ONTOLOGY_EXTRACT_PROMPT_VERSION = "v1"

EXTRACT_SYSTEM_PROMPT = """你是知识建模助手。用户提供一段源文本和一个本体的定义（含属性列表）。
你的任务：从源文本中识别属于该本体的对象实例，并为每个对象抽取属性值。

规则：
1. 只依据源文本，不得编造文本中没有的信息；没有依据的属性不要输出。
2. 对象名称使用文本中的规范称呼，简洁明确，避免长句。
3. 属性值使用文本原文表述并保持简洁；文本中找不到则不输出该属性。
4. 源文本中没有该本体的任何实例时，返回空列表。
5. 只输出 JSON 对象，不要输出任何其他文字。输出结构：
{"objects": [{"name": "对象名", "attributes": {"属性名": "属性值"}}]}"""

EXTRACT_SYSTEM_PROMPT_WITH_RELATIONS = EXTRACT_SYSTEM_PROMPT + """
6. 同时根据源文本，按给定的本体关系类型建议对象之间的关系（新对象之间，或新对象与
给定清单中的已有对象之间）。只建议文本中有明确依据的关系。最终输出结构：
{"objects": [...同上...],
 "relations": [{"source": "对象名", "relation": "关系类型名",
                "target": "对象名或已有对象名", "target_existing": true|false}]}"""

# USER_PROMPT 模板（渲染顺序）：
# 【本体定义】名称 + 描述 + 属性列表（名 + 描述）
# 【关系类型】（suggest_relations 时）每条：源本体名 -[关系名]-> 目标本体名 + 描述
# 【已有对象清单】（suggest_relations 时）库内对象 ≤300 个：本体名/对象名；超出则取前 300 并在结果 warnings 注明
# 【源文本】截断后的输入文本
```

模型选择：默认 llm_service 的 `provider.active_model`；body 可选 `model` 覆盖（透传 llm_service 模型映射，管理面已按域隔离配置）。

### 8.5 输出契约（LLM → 候选）

LLM 输出仅是**建议**，落库前全部走 §6.8 强校验。服务端解析后组装为：

```json
// GET /extract/{token} status=done 的 candidates
{ "objects": [
    { "name": "阿司匹林", "attributes": {"适应症": "发热、头痛"},
      "conflict": false, "conflict_with": null }        // 与库内已有对象重名 → conflict=true + 名字
  ],
  "relations": [
    { "source": "阿司匹林", "relation": "治疗", "target": "感冒", "target_existing": false,
      "endpoint_ok": true }                              // 端点预检：按关系类型与两端本体静态推断
  ],
  "warnings": ["已有对象清单超限，仅提供前 300 个；新对象与清单外对象的关系建议可能缺失"],
  "input_chars": 8321, "truncated": false }
```

- 冲突/端点标记**只影响 UI 提示**，不阻止用户勾选——最终以 instantiate 的强校验为准（冲突对象若强行提交会得到 422 定位）。
- relations 中引用的对象名解析规则：先在本批候选 `objects` 中找，再到库内已有对象中找；都找不到的候选直接丢弃并计入 warnings。

### 8.6 限制与失败处理

| 项 | 限制 |
|---|---|
| 文本长度 | ≤20000 字符（粘贴/文件/KB 文档统一），超出 400 `text_too_long` |
| 已有对象上下文 | ≤300 个给 LLM，超出截断 + warning |
| 候选对象数 | 单次 ≤100（超出只取前 100 + warning） |
| 任务有效期 | 1h；过期轮询 404 |
| 落库 | 仅 `POST /instantiate` 一条路，无自动落库 |

| AI 抽取 | prompt 渲染快照（版本冻结）、mock LLM 输出解析（含栅栏包裹/畸形 JSON）、候选组装（冲突/端点预检/未知引用丢弃）、超长文本 400、任务过期 404 |
| 权限 | 域成员写 403、跨域库 404、域管理员/站点管理员放行 |
